## 执行韧化协议

每个角色 prompt 头部必须执行 6 条：

1. **心跳信号（opt-in，Phase 0 显式同意才写盘）**：默认**不**写心跳文件——心跳是**已获 Phase 0 显式同意**才启用的**可观测性**能力（属「Operational Telemetry」manifest 段）。若已获同意，启动 30 秒内 + 每 5 分钟写自己的心跳文件 `run/<项目>/.tmp/<两位角色号>-<角色名>-heartbeat.md`（写明「启动时间 + 当前模型 + 状态=🔄 In Progress」），后续每 5 分钟追加 `[心跳 HH:MM] model=<model-id>`；**归属标识（v2.12.67，审计 P2-3）**：文件名两位角色号即心跳归属标识，主控三方对账时须与「该角色本轮 spawn 记录」匹配——**前缀与角色不符的心跳不采信**（防跨角色/跨项目心跳误配；零 exec 下不做加密签名）；**子代理不直接写 status.md**——status.md 由主控收到心跳信号后独占更新（子代理只读 status.md）。**写文件任务硬卡比读放宽 2 分钟**。
   > **用户告知**：心跳文件是**周期性磁盘写入**——运行期间约每 5 分钟一行，写入位置限 `run/<项目>/.tmp/`（仅当前项目目录，不写项目外、不写其他项目）。SKILL.md「执行前安全须知」与 QUICKSTART.md「重要警告」已向主人披露该写入。**披露 ≠ 同意**：`.tmp/` 心跳写盘**不因「运行本 skill」而自动生效**，必须由 Phase 0 显式同意关卡单独放行（见下条）；**未取得该同意前不创建、不追加任何 `.tmp/` 文件**。项目结束后 `.tmp/` 可整目录删除，不影响已交付产物。
   > **同意门（fail-closed）**：心跳写盘的**唯一**依据 = 主人对 Phase 0「将创建的文件清单」的**显式确认**，且清单**逐项**含 `.tmp/<两位角色号>-<角色名>-heartbeat.md`。**主控自动列清单 / 主人沉默 / 「反正本来就要写盘」的推断，都不构成同意**。缺该确认 ⇒ **不写 `.tmp/`、不开工**，并在 `01-任务简报.md` 记 `心跳写盘同意: 未取得`。说明：心跳属「Operational Telemetry」manifest 段，**已在本技能 manifest 中声明为 opt-in capability**；不属于隐含行为。

2. **分阶段 ack**：< 2 分钟启动 ack 即可；2-5 分钟启动 + 完成；5-15 分钟四段（25/50/75/100%）；> 15 分钟**禁止**——必须拆任务。完成 ack 的 token 消耗由**主控**从 completion event Stats 记录（子代理无需回传，教训 #256）。

3. **降级自报**：遇 provider 401 / 配额耗尽，在 final message 返回 `{"status": "degraded", "reason": "<错误摘要>"}` 后立即结束，**禁止 0 tokens 静默退出**（主控凭此触发 fallback 标注）。配额 vs ping 超时区别：主控 LLM 推理判定。

4. **超时硬卡**：T1-T3 10 / T4 12 / T5 15 / T6 15 / T7 12 / T9 10 / G14 8 分钟。提前 2 分钟写 `[警告] 已耗时 X 分钟`；提前 1 分钟必须 partial output；到点主控 kill + 接受 partial。

5. **禁止假装在线**：心跳 ack 必须真实反映进度；过程语言残留自检（M-Form-5）：完成后 检查「v2 稿/初稿/草稿/修订说明/主人结构性观察/据行业经验估算/论据类型」有命中立即删除。

6. **报告长度上限 + 超限分块（回应实测 #4）**：报告类产出（T4 分析大纲 / T6 批判 / G14 检测 / T7 审计 / T9 审稿 / T8 终检）**回传**

> ⚠️ **双上限口径（v2.12.27 修订 —— 对齐平台事实）**： **数值真源 = `phase-order.yaml` 各节点 `output_chars_max`（本节不重列数值）**。
> - **写盘上限** = `output_chars_max`（phase-order.yaml 各节点，12000/10000/15000 等）—— 产物文件可写到该长度
> - **回传上限** = **平台硬上限 4096 字符**（completion 事件 findings ≤ 4096 / 单条结果 ≤ 512 / 路由通知 ≤ 1024）—— **超限即被平台截断且不报错**
> - **因此**：大报告**一律写盘**，completion 回传**只带摘要 + 产物路径 + 「已写盘」声明**；需要完整内容时由主控 `read` 产物，**不依赖回传**。前自查长度（read 估行数/字符量级，零 exec 不跑 wc），**硬上限见 phase-order.yaml 各节点 `output_chars_max`**（T4/T6 ≤12k、T7 ≤10k、G14 ≤6k、T9 ≤15k、T8 ≤10k 字符）。超限**禁止一次性全量回传**——主动按结构分块回传（每块 ≤上限，主控逐块落盘拼接）；单块仍超 = 砍细节保结论（各维度结论 + 证据编号必留，展开论述可省）。全程禁止「先全量发出赌截断」：截断后主控侧拼接的段要标 `[主控拼接]`，属 fallback B 级（见 design 版分级）。

> 🧾 **超长报告分片预申报（v2.12.67，审计 P1-1：截断的事前设计，补 display-cap 事后捞取的结构性缝隙）**：只读档报告「全文置于交接回传」与平台 4096 静默截断叠加 ⇒ 超长报告的 completion 可能不完整且无可靠截断信号。故**事前协议**：
> - **触发线 3500 字符**（4096 减摘要与结构开销的保守线，**唯一真源 = 本条**）：按 §6 前置自查长度，超过即触发；
> - **final message 首块 = 分片清单**：`【报告分片 N/M】` + 每片指纹（`p<N>: 首行「…」 末行「…」 约<X>字符`），随后 M 段**连续输出**报告正文；分片按报告自然结构切（T6 按 C1-C7 / T7 按 G 门 / T9 按 6 维度 / G14 按 9 类），**禁跨段拦腰切**；
> - **主控对账**：按清单指纹逐片核对（首末行 + 量级）；缺片 / 指纹不符 ⇒ 走既有 display-cap 捞取（`sessions_history` 回收，不重跑）；拼接产物头部标 `[多块拼接产物]`（A 级，design §4.7 分级）；
> - **与 display-cap 三角的关系**：本协议**事前**（截断前已按片可控），display-cap 三角仍是**事后兜底**，叠加不互替；
> - **机械接线**：本段 + 四 dispatch 载体（T6/T7/T9/G14）分片话术的存在性由 flow-check 规则 42 守（防「协议从载体静默消失」，#427 同族）。

## 编排循环三防（交接点）

**spawn 后** 立即 `subagents(action=list)` 确认 runId 在 active runs；不在 = 重试 ≤2 次。

> ⚠️ **机械兜底边界（v2.12.62 显式声明，审计 B12）**：本节防的故障是「`sessions_spawn` 返回 accepted，但子会话实际不存在 ⇒ 主控无限等待」。论衡 agent **零 exec**，这类**运行期**故障**无法**在构建期被机械门拦住 —— 本协议是**纪律层**，其可机械部分只有两件：
> ① **留痕**：主控按本节验证后在 `status-template.md` 写 `spawn_landing: ok|missing|retry:<N>`（主人可事后核验，失败不再无声）；
> ② **接线**：协议文本必须同时存在于本文件与主控卡指针中（flow-check 规则 34），防「协议从载体里静默消失」。
> **不要把「本文件写了这条」误读为「门会拦住不验证」。**（同族诚实边界：checkpoint-card 呈现行为 / B12 本身。）
**yield 超时** 3 分钟无事件 = 查 subagent 状态 + sessions_history；状态正常继续 yield，状态异常补 spawn。
**超时取消（kill）** 子代理超硬卡阈值 → `subagents(action=cancel, taskId=<来自 list 的 taskId>)` 终止（零 exec 下唯一合法终止方式，不 exec kill 进程）；取消后再 `subagents(action=list)` 复核是否真停（取消可能不完整，未停则重试 cancel，幂等）。
**完成事件幂等** 收到 Done 先查 status.md 是否已 Done，是 = duplicate 忽略。

## 端到端活体冒烟协议（v2.12.72 批次 3-D）

> **目的**：验证「构建期门全绿」之外的运行期链路：真实 spawn、落地、交接回传、审计链、M 门对账与 status.md 更新。冒烟**不进 CI**，每次升版或流程大改后由维护者/主人执行一次。

### 两级范围

- **L1 机制冒烟**：至少真实 spawn T1/T2 两个叶子 worker，核验 `spawn_landing`、心跳/产物落盘、completion 回传（含 Stats line 或如实记缺失）、主控交接复验；不自动通过任何 owner_checkpoint。
- **L2 全流程冒烟**：约 3000 字轻量档，走 T1/T2 + T3 空卡协议 + T5 + T7 + T7.5 + G14 selfcheck + final assembly + T8；T6 必跳、T4 可省、T9 按轻量档决定。Phase 0/2.5/3.5/5 四个人在环节点仍须主人明确决策，测试模式不得把沉默当通过。

### 通过判据与留痕

1. 每个实际 spawn 均有 `spawn_landing: ok|missing|retry:<N>`，每个完成节点均通过「产物存在、数量对账、完成标记、新鲜度」复验。
2. status.md 留 `smoke_level`、`smoke_run_id`、`smoke_started_at`、`smoke_finished_at`、`smoke_verdict`，并保留各节点 `spawn_landing` 与 M 门记录。
3. L2 另核对 T2.5/T7.5、审计报告、最终交付说明和 status.md 的阶段状态互相对得上；任一缺失 = `fail`，不得用纸面门结果替代。
4. 结果摘要回填 [`performance-benchmarks.md`](performance-benchmarks.md) §六；Stats line 缺失、worker 接管、owner 决策等待均如实登记。

> ⚠️ **诚实边界**：冒烟消耗真实 token/子代理且受外部服务与主人决策影响；L1 不是内容质量验收，L2 也不等于每个主题的质量保证。冒烟只证明本次活体链路是否跑通，不得反推所有未来运行必然成功。

     - **修订 SOP（教训：AI安全隐患实战 P1-2）**：修订版本管理遵循写手卡「修订标准操作块」——先 `cp drafts/初稿-vN.md drafts/初稿-v{N+1}.md` 再改 v{N+1}，vN 保持原始；中间态/备份移入 `drafts/archive/`；status.md 修订回环记录时间戳与文件 mtime 对齐；主控校验 v{N+1} 哈希 ≠ vN。
     - **进入局限性模式是正常路径**：主控不得因为「不想进入 Acknowledged Limitations 模式」而放松标准放行 P0/P1。进入局限性模式是论衡设计内的诚实出口，不是失败——「通过 ≠ 完美，诚实陈述剩余风险 > 假装完美」。主控判「打回」应严格基于 P0/P1 是否关闭，而非对局限性的排斥。
     - **修订二分类（教训 #283）**：明确区分「T7 打回修订」vs「主控触发修订」，后者**不计入修订回环预算**（登记；轮次口径唯一真源 → [`../真源/pipeline-overview.md`](../真源/pipeline-overview.md)『修订回环仲裁规则』）。

       | **A. T7 打回修订**（结构性 P0/P1） | T7 审计报告判定 P0/P1 未关闭 | **是** | **必须** spawn 独立写手 v{N+1}（保持论证独立性） | 主控只派发 + 收产物，不代改 |
