## 二、status.md 并发写控制

**status.md 主控独占写**：实战中主控 edit status.md 失败 2 次（子代理改了 status.md 内容），主控和子代理并发写有 race condition。**v2.3.7 升级后协议**：
- **主控独占写**：`status.md` 只能由主控（主 agent）写入，子代理**不得直接 `write`/`edit`** status.md——子代理通过心跳文件（如 `run/<项目>/.tmp/<role>-heartbeat.md`）向主控发信号，主控按心跳节奏独占写入 status.md
- **子代理标识状态**：子代理在产物路径写**自己的阶段文件**（如 `drafts/<role>-status.json`），主控轮询阶段文件后更新到主 status.md

### v2.5.5 结构化重写（教训 #166，主人实测反馈）

原 markdown 表格 7 列 + 主控 edit 频繁失败（空格漂移 / old_string 不匹配 / 重复行 bug）。实战《口腔 AI》+《论艺术中的丑》两次项目都遇到。

**主控更新 status.md 改用「key:value 文本替换」**：

- **角色状态行替换策略**：`**T5 写作**: ⬜ Inbox` → `**T5 写作**: ✅ Done (2026-08-25 11:30, 5686 字)`（一行替换，零空格依赖）
- **闸门清单**：保留 `- [ ]` 格式（仅打钩，**主控不用 replace**）
- **产物路径**：`final/定稿: final/定稿.md` key:value 格式（路径不变，仅替换 value）
- **方法论足迹**：保留表格（实时数据有数字变化，主控用 row replace，但实战发现这里漂移最多 → 考虑也改文本）

**实战检验**：口腔 AI 实战 status.md 表格空格漂移 3 次 / 论艺术中的丑实战表格空格漂移 2 次 → 重写后预期零漂移。

### 子会话回执复验门（教训 #191）

> **背景**：子会话「完成回报」 ≠ 写盘证据。教训 #191 实证：v1→v2 修订子会话回报「完成 13/13」，但 `ls drafts/` 显示 v2 文件从未被写盘。子会话回执本身**也是子会话生成**，不可作为自我验证。

**主控复验 4 件套**（收到任何「完成」汇报必跑）：

1. **ls 实证**：产物路径存在 + 非空
2. **wc 实证**：行数/字节数与子会话回执报告数**对得上**（差值 > 20% 即异常）
3. **grep 关键标记**：修订类必 grep 完成标记（`<!-- P[0-2]-.*✅`）数 = 任务书条数
4. **时间戳检查**：`find . -newer <任务书路径> -type f` 应包含产物

**不通过处理**：
- 4 件套任一不过 → 退回子会话补写（不直接转报主人）
- 子会话二次仍不过 → 主控亲自 edit + 记教训（不连续第三次 spawn 同任务）

## 十二点五、子代理错误码语义分层（教训 #234）

> **背景**：v2.10.3 首测主控误判——GLM-5.3 真实产物被当「未写盘」，主控做无效兜底。根因：主控把「资源/认证层错误」和「产物缺失」混为一谈。

**错误码分层（收到子代理报错时先分层，再决定是否兜底）**：

| 错误类型 | 典型信号 | 产物状态 | 主控动作 |
|---------|---------|---------|---------|
| **资源/认证层错误** | HTTP 401/403/429 / quota exceeded / 欠费 | **产物可能已完整写盘** | 先 `read` 验证产物，**不立即兜底** |
| **工具调用错误** | tool_error / protocol 错误 | 产物可能部分 | `read` 验证 + 补缺 |
| **显式未完成** | status=incomplete / degraded | 产物缺失或部分 | 按 degraded 协议走 fallback |

**主控兜底声明格式**：兜底时必须在产物头部 + status.md 写「**子代理实际工作 vs 主控叠加**」分层记录，不得笼统称「主控兜底」：
- 子代理实际产出：<列出子代理已写盘的内容>
- 主控叠加：<列出主控补写的内容>

**修复教训 #234 的核验顺序**：cp / 兜底之前，先 `read` 确认产物是否已存在、是否与子代理回传一致——**先 diff/grep 确认，再决定 cp 或兜底**。

## 十八、「据行业经验估算」限定使用条件（教训 #44，回应 ClawHub 92% finding）

> 背景：v2.0.7 主控洞察融合协议允许使用「据行业经验估算」软化未源化数字。但 ClawHub 安全审计指出这会成为「hedging language loophole」—— agent 可随意用该措辞让未经验证数据通过审计。

**限定使用条件**（满足**全部**才能使用）：
1. **三源检索全失败**：① T1 文献检索 + ② T2 数据检索 + ③ web_search 补充均**未找到任何可引用的数字**
2. **段落顶部加注**：每次使用前在该段落开头写明 `[行业估算，非数据卡]` 标记
3. **附估算依据**：该数字必须能基于「业内常识」「从业者经验」「结构性推理」之一推导（不能凭空出现）
4. **不超过全文 3 处**：全文章「据行业经验估算」类措辞累计 ≤3 处（防止滥用）
5. **T7 审计必查 G2.5 估算标记**：T7 在 G2 数据溯源里加一条专门查估算使用频次，超过 3 处 → P1

**禁止使用的场景**：
- ❌「据行业经验估算」+ 具体百分比/元数（更精确 = 更需数据卡）
- ❌ 同一论点同时使用数据卡数字 + 估算（混用 = 不可验证）
- ❌ 全文结论性数字（必须可溯源）

**示例**：
- ✅ 正确：开模打样成本「据行业经验估算」动辄「数十万元」（有范围、无精确值）
- ❌ 错误：开模打样成本「据行业经验估算」47 万元/ SKU（伪装精确度）
- ❌ 错误：同一段同时使用 D15（顾家 184.8 亿）+ 估算数字（数据混用）
- 写手收到含主人洞察的指令时，按本协议做转换；如拿不准，**默认 A 档客观化**

## 二十三、编排循环防空转（教训 #102，2026-08-19 ECS 实战）

> **背景**：T8→T5 交接点被 duplicate 完成事件打断，spawn T5 的 tool call 丢失，主控空转 2.5 小时。根因：push-based 编排循环过度依赖「完成事件恰好投递一次」。

**主控在 T 角色交接点必须遵守的三道防御**（详见 [`_shared/执行韧化协议-exec.md`](../_shared/执行韧化协议-exec.md) § 4）：

1. **spawn 后立即验证落地**：每次 `sessions_spawn` 后用 `subagents(action=list)` 确认 runId 在 active，没出现 = spawn 丢失，立即重试（≤2 次）
2. **yield watchdog**：yield 后 3 分钟无完成事件 → 自查 `subagents(action=list)`（回应 A.I.G T05），判断 spawn 丢失空转还是子代理真在跑
3. **完成事件幂等**：收到某角色完成事件时先查 `status.md` 该角色是否已 Done，已 Done = duplicate 事件，**忽略不重复推进**
4. **交接点「三段式 spawn」**：T8→T5、T4→T8、T5→T4（修订）禁止「spawn → 直接 yield」，必须「spawn → 验证落地 → 确认后 yield」

**主控 spawn 验证落地伪代码**：
```python
run = sessions_spawn(task=...)
if not subagents_has_active(run.runId):
    log("[#102] spawn runId={} 未落地，重试".format(run.runId))
    run = sessions_spawn(task=...)
```

**完成事件幂等伪代码**：
```python
def on_completion(role, runId):
    if status_md[role]['state'] == 'Done':
        log("[#102 幂等] {} 已在 Done，忽略 duplicate runId={}".format(role, runId))
        return
    status_md[role]['state'] = 'Done'
    spawn_next_role()
```

**诊断（spawn 链空转排查）**：
```bash
cd ~/.openclaw/agents/<agent>/sessions/
F=$(ls -t *.trajectory.jsonl | head -1)
echo "spawn: $(grep -c '"sessions_spawn"' $F) / yield: $(grep -c '"sessions_yield"' $F)"
# yield > spawn = 空转嫌疑
grep -oE 'session_key: agent:[a-z]+:subagent:[a-f0-9-]+' $F | sort | uniq -c | sort -rn | head -5
# 同一 subagent uuid >1 次 = duplicate 完成事件
```
     - **「轮」的定义**：**0 轮**=T5 出 v1；**1 轮**=v1→v2（融入主人洞察 Phase 3.5 + T6/G14 反馈）；**2 轮**=v2→v3（T7 打回修订或 T8 亲修）；v3 后 minor cosmetic 由 T8 inline 不计轮，结构性 P1/P0 须主人拍板启 T5 v4 + Acknowledged Limitations。完整仲裁表见 SKILL.md「修订回环仲裁规则」
     - **T8 小幅修补权限（教训 #120，字数超限红线）**：T8 从「只做签字」升级为「可做小幅修补」——✅ 可修：≤字数 5% / AI 披露修正 / 元叙事清理 / P1-D 事实错误（引用格式/元数据/漏引/拼写）；❌ 不可修：结构性（P1-A/B/C 论证补强/结构缺失/反方缺失）+ P0 → 必须启 T5 独立写手。**⚠️ 字数超限红线（实战教训）**：终检发现字数超限（按 [`_shared/字数判定表.md`](../_shared/字数判定表.md) P1/P0）→ **spawn T5 v3 精简，主控只核验不 edit**（T8 亲自 edit 补字/改写会越界成「代写」，且可能把字数越改越超——实战 T8 5 处 edit 把 0.7% 超推成 3.4% 超）

     - **为什么 ≤2 轮**：「不要无限循环。无限循环是 LLM 的舒适区陷阱」—— 论衡主人口吻（教训 #64）
     - **修订轮强制独立写手（教训：AI安全隐患实战）**：修订轮**必须 spawn 独立写手子代理**执行，主控只做协调与派发，**不得由主控代为执行修订**。理由：论衡 9 角色独立的核心价值是「独立角色互为镜像，防止自我说服」——若主控既协调又亲自改稿，等于一个人既当运动员又当裁判，**T7** 审计的独立性被削弱。正确做法：**T7** 产出修订任务书 → 主控 spawn 独立写手 v2/v3 按任务书执行 → 写手更新 drafts/初稿-vN.md + 修订说明 → 主控交 **T7** 复核。
     - **边界澄清（教训：AI安全隐患实战 P1-4 + #120）**：本条与 v2.1.3「小修订主控直接 edit」的边界，v2.3.1 按 P1 分级重划——**「T7 打回后的正式修订轮」**：结构性 P1（A/B/C）+ P0 → 必须 spawn 独立写手（无论几处）；**P1-D 事实错误（引用格式/元数据/漏引/拼写）+ 元叙事清理 + AI 披露修正 + ≤5% 改动 → T8 主控亲修**（慢活快改，不涉论证独立性）。判定口诀：**「P1 是结构性还是事实错误？」**——结构性 → spawn 写手；事实错误 → T8 亲修。实战 P1-4 根因：主控按 v2.1.3 旧条款合理化了自己代执行第 1/2 轮结构性修订。
     - **修订 SOP（教训：AI安全隐患实战 P1-2）**：修订版本管理遵循写手卡「修订标准操作块」——先 `cp drafts/初稿-vN.md drafts/初稿-v{N+1}.md` 再改 v{N+1}，vN 保持原始；中间态/备份移入 `drafts/archive/`；status.md 修订回环记录时间戳与文件 mtime 对齐；主控校验 v{N+1} 哈希 ≠ vN。
     - **进入局限性模式是正常路径**：主控不得因为「不想进入 Acknowledged Limitations 模式」而放松标准放行 P0/P1。进入局限性模式是论衡设计内的诚实出口，不是失败——「通过 ≠ 完美，诚实陈述剩余风险 > 假装完美」。主控判「打回」应严格基于 P0/P1 是否关闭，而非对局限性的排斥。
     - **修订二分类（教训 #142）**：明确区分「T7 打回修订」vs「主控触发修订」，后者不占用常规 2 轮预算（登记，见 SKILL.md 仲裁表）。
       | 修订类型 | 触发场景 | 是否计入 ≤2 轮 | spawn 独立写手 | 主控介入边界 |
       |----------|---------|---------------|--------------|------------|
       | **A. T7 打回修订**（结构性 P0/P1） | T7 审计报告判定 P0/P1 未关闭 | **是** | **必须** spawn 独立写手 v{N+1}（保持论证独立性） | 主控只派发 + 收产物，不代改 |
       | **B. 主控触发修订**（字数压缩 / 微调） | 主人决策（如「字数压缩」/「加 1 段」）/ 主控误判字数 / T5 v5 教训 #142 类 | **否**（否，不占 2 轮预算） | 可由主控代修（≤5% 改动）+ spawn T5 写手独立验证（主控触发的 spawn 也算独立写手，不算 T7 打回） | 主控可直接 edit，但 T7 需复核 |
       | **C. T8 终检亲修**（事实错误 ≤5%） | T7 打回 P1-D 事实错误 / 引用格式 / 元数据 | **否** | 主控亲修（不变论证独立性） | 主控可在 status.md 标「T8 亲修」 |
       - **判定口诀**：
         1. T5 spawn 是**主控触发**还是**T7 打回**？查 status.md spawn 事件的 `trigger` 字段
         2. 主人决策（如「字数压缩到 1 万字」） → 主控触发修订（B 类）
         3. T7 审计报告 P0/P1 → T7 打回修订（A 类，计入 ≤2 轮）
         4. 引用格式错误（[L03] 写错成 [L30]）→ T8 亲修（C 类）
       - **实战背景**：主人决策 B 触发 T5 v3 压缩（主控触发 B 类）+ T5 v5 多余操作（4m9s 死循环，教训 #142，因为主控误判字数 → 重复 spawn）→ v2.3.7 升级后主控触发修订明类为 B，**不占用常规 2 轮预算（登记，见仲裁表）**（v3 已经过 ≤2 轮检查），T5 v5 需主控验证「上一版最终态字数」（stat 真实 mtime，不读 mtime 中间态）。

## 二十五、Archive 清理策略（教训 #161）

**主控 Phase 5 终检时按任务简报「archive_strategy」字段清理 drafts/archive/**：

| 策略 | 处理 | 适用场景 |
|------|------|---------|
| **keep_last_2**（默认）| 保留 v{N-1} + v{N}（最近 2 版），删除 v{N-2} 及更早 | 生产场景 |
| **keep_final** | 仅保留最终版（v3），删除中间态（v1/v2）| 交付场景 |
| **keep_all** | 全保留| 教学/调试场景 |

**操作 SOP**：
1. Phase 5 终检前，主控读任务简报「archive_strategy」字段
2. 按策略列出待删文件清单（保留最终版 + 修订说明最新版）
3. 主控在 status.md 终检段写明 `[archive HH:MM] 按 {strategy} 清理 drafts/archive/，保留 N 文件，删 M 文件`
4. **不自动执行删除**——主控列出清单 + 主人决策执行（防误删）

**实战背景**：v1/v2/v3 + 修订说明 ×3 = ~100KB archive/，按 keep_last_2 策略只需保留 v2 + v3 = ~30KB。

**为什么不自动执行**：
- v2.0.2 起反哺报告不自动 commit = 主人 review 原则
- 清理 archive 也按同样原则——主控只列清单，主人决策
- v2.5.6 评估是否升级为自动执行（实战反馈后再定）

## 二十六、T9 扩写/改写清单承接协议（教训 #168）

T9 跑完后主控必询问主人 3 选项（主人《论艺术中的丑》反馈）：

```
## T9 评审完成 + 主人决策

T9 总评分：XX/30
建议：accept / minor / major / reject
目标期刊适配：《XX》（匹配度 X%）
扩写/改写清单：见 audits/审稿报告-v{N}.md 末段

**主人决策**：
- □ A. 接受现状定稿，投稿（不修订，Phase 5 终检直接交付）
- □ B. 触发扩写修订（**B 类修订，不占用常规 2 轮预算（登记，见仲裁表）**，主控 spawn T5 v4 写手，prompt 附 T9 扩写清单作为任务书）
- □ C. 换期刊（字数匹配 5000 字，选其他期刊）
- □ D. 主人明示其他调整

**触发 B 类修订**（主控确认后）：
1. 主控读 T9 报告末段「扩写/改写清单」
2. 主控同步修改任务简报「目标篇幅」字段（如果扩写）
3. 主控 spawn T5 v4 写手，prompt 显式附：
   - 「基于 drafts/初稿-v{N}.md 扩写」
   - 「目标期刊要求：XXX」
   - 「扩写清单：...（逐条）」
4. T5 v4 完成后 → T7 审计 → T8 终检 → 主人最终验收

**为什么不自动触发**：
- v2.0.2 起反哺报告不自动 commit = 主人 review 原则
- T9 扩写建议也按同样原则——主控列出建议，主人决策
- 实战中 T9 建议可能与主人战略冲突（如不想投稿该期刊、不想扩写）
- 主控不替主人做战略决策
```

**实战背景**：主人《论艺术中的丑》T9 建议「投《文艺研究》需扩写 8000+ 字」，但字数在 Phase 0 定死 = 5000 字 → T9 建议无处承接。v2.5.5 后 T9 输出「扩写清单」+ 主控决策 B 类修订。

**B 类修订与 ≤2 轮的关系**（教训 #142）：
- A 类（T7 打回结构性 P0/P1）→ 计入 ≤2 轮
- B 类（主人决策触发，包括字数压缩/扩写/换期刊）→ **不占用常规 2 轮预算（登记，见仲裁表）**
- C 类（T8 亲修 P1-D 事实错误）→ 不占用常规 2 轮预算（登记，见仲裁表）

主控在 spawn T5 v4 时 prompt 显式标「[B 类修订触发 = 主人决策扩写]」+ status.md 修订回环记录「**B 类 v4 主控触发扩写**」。
