## 二、status.md 并发写控制

**status.md 主控独占写**：实战中主控 edit status.md 失败 2 次（子代理改了 status.md 内容），主控和子代理并发写有 race condition。**升级后协议**：
- **主控独占写**：`status.md` 只能由主控（主 agent）写入，子代理**不得直接 `write`/`edit`** status.md——子代理通过心跳文件（如 `run/<项目>/.tmp/<role>-heartbeat.md`）向主控发信号，主控按心跳节奏独占写入 status.md
- **子代理标识状态**：子代理在产物路径写**自己的阶段文件**（如 `drafts/<role>-status.json`），主控轮询阶段文件后更新到主 status.md

### 结构化重写（教训 #166，主人实测反馈）

原 markdown 表格 7 列 + 主控 edit 频繁失败（空格漂移 / old_string 不匹配 / 重复行 bug）。实战《口腔 AI》+《论艺术中的丑》两次项目都遇到。

**主控更新 status.md 改用「key:value 文本替换」**：

- **角色状态行替换策略**：`**T5 写作**: ⬜ Inbox` → `**T5 写作**: ✅ Done (2026-08-25 11:30, 5686 字)`（一行替换，零空格依赖）
- **闸门清单**：保留 `- [ ]` 格式（仅打钩，**主控不用 replace**）
- **产物路径**：`final/定稿: final/定稿.md` key:value 格式（路径不变，仅替换 value）
- **方法论足迹**：保留表格（实时数据有数字变化，主控用 row replace，但实战发现这里漂移最多 → 考虑也改文本）

**实战检验**：口腔 AI 实战 status.md 表格空格漂移 3 次 / 论艺术中的丑实战表格空格漂移 2 次 → 重写后预期零漂移。

## 三、任务书工具边界声明

每次 spawn 子代理的任务书必含「本环境无 exec/process/shell 工具，禁止尝试；验证用 read 工具」声明，防子代理误试 exec 空转（本机测试 minimax-m3 误试 exec 致交接异常）。

**v2.12.8 新增：任务书必含叶子声明**（与上句并列，同一次 spawn 写）：

> 你是本流水线的**叶子 worker**：不得调用 `sessions_spawn` 派生任何子代理，不得用 `subagents` / `sessions_list` / `sessions_history` 查看或管理其他会话（平台默认开启递归委派，你可能「拿得到」这些工具，但未被授权）。需要额外检索/人手 → 在交接报告写「需求回执」（缺什么/为何缺/建议派谁），由主控决定。

**背景（教训 #306）**：平台可能默认开启有界递归委派，子代理实际拿得到 `sessions_*` 递归工具；而 announce 链逐级上传、主控只收直接子级——子代理自行 spawn 的孙辈产物**不上传主控**，等于产出静默丢失 + token 已花。**主控侧自检**：**标准架构恒为多 Agent 九角色**，按叶子架构派发（直接子代理即叶子），并在每次 spawn 的任务书内确认叶子声明已写 → `status.md` 记派发清单；worker 失败/不可用 ⇒ 只接管该节点并记录。**论衡不读取、不校验、不修改宿主的权限配置文件 / 网关配置**（不读宿主配置、不就宿主配置告警）；**自身会话可见工具面仍做非侵入式自检与披露**（见本文件「能力自检」段；精确口径真源 = [`_shared/external-services.md`](../_shared/external-services.md) §「不读取宿主网关配置（精确口径）」）。

## 四、案例检索并行化（教训 #267）

- **并行触发**：通过 `pre_spawn_enforcement` 前置核验后，主控并行 spawn T1 + T2 + T3 三个独立 sessions
- **0 条场景降级协议**（cases = 0 时）：T3 spawn 但 prompt 写「本次任务无案例需求，输出空案例卡 + 显式声明 `本次无案例需求，N 条案例卡`」

3. **「报告后激活」重跑时序**：凡前提为「相关报告已落盘」的检查项，**必须在报告落盘后重跑**；主控预跑结果不得直接当闸门输入（节点级标注 = `phase-order.yaml` 的 `rerun_after_report`）。

## 十二、完成验证铁律

收到任何角色「完成」报告，**第一动作是验证产物**而非采信报告：
- `ls -la <产物路径>` 确认存在 + 非空
- 关键内容 grep（初稿 grep 章节标题、数据卡 grep `[D01]`、审计报告 grep 「结论」）
- **文件落地 stat 校验**：永远不信 write 工具回报的字节数——中文 UTF-8 占 3 字节

**循环检测**：子代理「假在线」（有 tokens 输出但无推进）也要兜底——`sessions_history` 查循环（连续 3 次重复短语 → 触发兜底 + 兑底）。

### 子会话回执复验门（教训 #259）

> **背景**：子会话「完成回报」 ≠ 写盘证据。教训 #259 实证：v1→v2 修订子会话回报「完成 13/13」，但 `ls drafts/` 显示 v2 文件从未被写盘。子会话回执本身**也是子会话生成**，不可作为自我验证。

**主控复验 4 件套**（收到任何「完成」汇报必跑）：

> ⚠️ **语义口径**：以下「ls / wc / grep / find / stat」描述的是**语义等价动作**（产物存在性、数量对账、标记计数、时间戳新鲜度），主控用 `read` / `sessions_history` / 文件元数据**推理实现**，不执行任何 shell；论衡零 exec。下列命令形态仅为语义说明，主人可在 host shell 手动复核。

1. **产物存在性**：产物路径存在且非空
2. **数量对账**：产物行数/字节数与子会话回执报告数**对得上**（差值 > 20% 即异常）
3. **完成标记计数**：修订类必核完成标记（`<!-- P[0-2]-.*✅`）数 = 任务书条数
4. **新鲜度**：产物修改时间**晚于**任务书

**节点推进前置校验（v2.12.28 新增 —— 防「跳步」）**：

每跑完一个节点、**推进到下一个节点之前**，主控**必须**核验三件：

1. **`next` 目标存在**：`phase-order.yaml` 里该节点 `next` 指向的 id **必须在 `pipeline` 中真实存在**（注意区分「节点 id」与「动作名」）；
2. **产物存在**：该节点的**产出**（yaml `output` 声明；无声明则按阶段文档的产物路径）在磁盘**真实存在**；
3. **不满足即停**：任一不满足 → **停下报错并告知主人**，**不得**凭「看起来做完了」继续推进。

> ⚠️ **反面实例（2026-09-11 实测）**：`t5_feedback_revision` 因当时无文档层编号被误判为 `audit_revision`（别名「Phase 4.2」），主控遂按 `audit_revision.next`（= `t7_5_integrity`）推进，**整段跳过 `t7_audit`** → 论文在**没有 T7 审计**的情况下交付。

**交付说明产物清单核验（v2.12.28 新增）**：`final/交付说明.md` 的产物清单**每一条都必须逐条核验存在性**（`read` / 文件元数据语义核对）；**清单中不得出现未落盘的产物**；核验结果记 `status.md`。
> ⚠️ **反面实例（2026-09-11 实测）**：交付说明声称「`audits/` 审计报告.md（v1 + v2 + v3 三轮）」—— **该文件并不存在**（T7 从未运行）。**交付物对自己撒谎是最危险的一类缺陷。**

**spawn 后 SOP（零 exec 语义版 —— **本段即唯一真源**，不再另设第二套）**：
1. **spawn 后不轮询、不 sleep** → `sessions_yield` 等 completion 事件（平台准则：不要用 `exec` sleep 搭轮询）
2. **收事件后跑「复验 4 件套」**（上文 1-4 条，全部以 `read` / 文件元数据语义等价实现）
3. **零产物 ∧ 超过该角色 `runTimeoutSeconds`**（见 SKILL.md「硬卡阈值表」）→ 主控亲写兜底 + `status.md` 记 `failed_silent_watchdog` + 告知主人；**不重试 spawn 同一任务**
4. **token**：从 completion event 末尾 Stats line 取（精确值）
5. **sha256 不跑**：主人可在 host shell 手工算后填回（既有口径，论衡 LLM 不计算）
6. **兜底唤醒（v2.12.56 P-2，与第 1 条并存不冲突）**：spawn 后**必须**安排一次定时自唤醒（触发时间 = 该角色硬卡阈值 + 缓冲）；到点**主动 `read` 核对磁盘产物**。**推进判据以磁盘产物为准**，completion event 仅作**加速信号**。第 1 条「spawn 后不轮询、不 sleep、用 `sessions_yield` 等完成事件」**不变**——兜底唤醒是**补充**，专治「worker 收尾挂起 → 完成事件不达 → 主控零动作」的无人值守环（2026-09-18 实测）。唤醒面以本 skill 声明为准（**不得调用未声明工具**）；宿主无可用定时面 ⇒ 退化为「下一次进入本会话即复核」+ `status.md` 记 `watchdog_unavailable`（不得静默）。⚠️ 方案原文示例的 `automations` **在 `denied` 内**，本协议**不授权调用**——启用须另行评审（本版不改 `denied` / `coordinator_only`）。

## 十二点五、子代理错误码语义分层（教训 #285）

> **背景**：v2.10.3 首测主控误判——GLM-5.3 真实产物被当「未写盘」，主控做无效兜底。根因：主控把「资源/认证层错误」和「产物缺失」混为一谈。

**错误码分层（收到子代理报错时先分层，再决定是否兜底）**：

| 错误类型 | 典型信号 | 产物状态 | 主控动作 |
|---------|---------|---------|---------|
| **资源/认证层错误** | HTTP 401/403/429 / quota exceeded / 欠费 | **产物可能已完整写盘** | 先 `read` 验证产物，**不立即兜底** |
| **工具调用错误** | tool_error / protocol 错误 | 产物可能部分 | `read` 验证 + 补缺 |
| **显式未完成** | status=incomplete / degraded | 产物缺失或部分 | 按 degraded 协议走 fallback |

**主控兜底声明格式**：兜底时必须在产物头部 + status.md 写「**子代理实际工作 vs 主控叠加**」分层记录，不得笼统称「主控兜底」：
- 子代理实际产出：<列出子代理已写盘的内容>
- 主控叠加：<列出主控补写的内容>

**修复教训 #285 的核验顺序**：cp / 兜底之前，先 `read` 确认产物是否已存在、是否与子代理回传一致——**先 diff/grep 确认，再决定 cp 或兜底**。

### 能力自检

**背景**：五档白名单**不能被机械强制**（`sessions_spawn` 无 `toolsAllow`）。本修订不改这一事实，而是把它从「纯声明」升级为「**可观测 + 可阻断**」：

- **主控侧（Phase 0 必走）**：核验自身可见工具是否**超出** frontmatter `metadata.tools` documented 集；超限项逐条记入 `status.md`「能力自检」段，并**在 Phase 0 向主人披露**（不阻断——主控工具面由宿主决定）。
- **子代理侧（每次 spawn 的首步）**：子代理按 [`_shared/dispatch-header.md`](../_shared/dispatch-header.md)「启动自检」核验自身工具面是否符合本档白名单，**按两级判据分开处置（v2.12.32 修订：工具面 ≠ 调用）**：**铁律：工具面超限 ≠ 调用许可**（超限只说明平台给的工具面比本档声明宽，不授权调用其中任何工具）；① **工具面超限 = 警告级**（属常态 → 记录 + 披露 + **呈主人裁决**：敏感题材可要求主控接管该 worker；未裁决前仅继续手头已授权动作，**不调用任何超限工具**）；② **实际调用越权工具 = 阻断级**（停止、不写盘、回报 `capability_excess`）；③ 主控未给裁决时返回 `degraded` 并**继续执行**。
- **阻断规则**：主控收到 `capability_excess` ⇒ **不采纳该产物**，记录并告知主人；若**实际调用**涉及 `exec` / `process` / `browser` / `terminal` / `sessions_*` ⇒ **该档停用**，改走主控接管该节点并披露。
- **⚠️ 工具面提示不等于调用越权**：当前会话可见工具多于本角色声明时，不中止、不要求宿主处理；只要未实际调用未声明工具，角色照常工作。实际调用未声明工具才停止、拒收产物并走主控接管。
- **记录位**：`status.md`「能力自检」段（主控工具面 / 各档子代理自检结果 / 越权回报）。
- **诚实边界**：本自检只约束本角色自己的调用行为，不读取宿主配置；工具面可见范围由 OpenClaw 平台负责。实际调用未声明工具才阻断并转主控接管，不产生任何宿主侧状态。

### 架构声明（v2.12.46 定案：标准架构恒为多 Agent 九角色）

**背景**：OpenClaw 原生提供多 Agent 与子代理能力。论衡只声明派发清单、角色边界与接管记录；宿主工具策略、沙箱和额外机械限制属于平台/宿主责任，不是本 skill 的前置条件。

- **唯一标准架构**：**多 Agent 九角色流水线**——T1-T7/T9/G14 各自落盘角色产物；主控 T0/T8 负责状态、权威同步、配图、定稿组装、终检
- **不设总开关**：架构恒为标准模式，不存在启动/关闭多角色的开关项
- **触发时机**：首次 spawn 子代理前，于 Phase 0 简报中说明派发清单
- **worker 接管（异常路径）**：worker 失败/不可用 ⇒ **只接管该节点**（`on_worker_failure`），status.md 记接管记录 + 交付说明披露 L1 独立性影响。⚠️ **例外（v2.12.55 S-2）**：`independence: blind_review` 节点（当前 = T9）**禁主控接管** —— 只能重试 spawn 独立子代理，仍失败则记 `missing_blind_review` + 显式告知主人（真源 = [`_shared/phase-order.yaml`](../_shared/phase-order.yaml) `t9_review.independence_failure_policy`）
- **敏感题材**：主人可**显式要求**主控接管涉密 worker 节点（其余节点照常派发）
- **论衡不读取、不修改宿主配置，也不对宿主的权限设定作任何前提假设**
- **记录位置**：status.md「项目元数据」段 `**架构**: 多 Agent 九角色` + 「worker 接管记录」（**不记 deny 明细、不记 enforcement 等级**）

### 不读取宿主配置

**核心承诺**：论衡运行**不调用、不读取、不干预**宿主 gateway / config / 任何宿主配置读取工具。**无例外**。

## 十八、「据行业经验估算」限定使用条件（教训 #44）

> 背景：v2.0.7 主控洞察融合协议允许使用「据行业经验估算」软化未源化数字。但平台审核指出这会成为「hedging language loophole」—— agent 可随意用该措辞让未经验证数据通过审计。

**限定使用条件**（满足**全部**才能使用）：
1. **三源检索全失败**：① T1 文献检索 + ② T2 数据检索 + ③ web_search 补充均**未找到任何可引用的数字**
2. **段落顶部加注**：每次使用前在该段落开头写明 `[行业估算，非数据卡]` 标记
3. **附估算依据**：该数字必须能基于「业内常识」「从业者经验」「结构性推理」之一推导（不能凭空出现）
4. **不超过全文 3 处**：全文章「据行业经验估算」类措辞累计 ≤3 处（防止滥用）
5. **T7 审计必查 G2.5 估算标记**：T7 在 G2 数据溯源里加一条专门查估算使用频次，超过 3 处 → P1

**禁止使用的场景**：
- ❌「据行业经验估算」+ 具体百分比/元数（更精确 = 更需数据卡）
- ❌ 同一论点同时使用数据卡数字 + 估算（混用 = 不可验证）
- ❌ 全文结论性数字（必须可溯源）

**示例**：
- ✅ 正确：开模打样成本「据行业经验估算」动辄「数十万元」（有范围、无精确值）
- ❌ 错误：开模打样成本「据行业经验估算」47 万元/ SKU（伪装精确度）
- ❌ 错误：同一段同时使用 D15（顾家 184.8 亿）+ 估算数字（数据混用）
- 写手收到含主人洞察的指令时，按本协议做转换；如拿不准，**默认 A 档客观化**

> **kill 的工具映射（零 exec，权威定义）**：论衡主控「kill 超时子代理」= `subagents(action=cancel, taskId=<来自 subagents(action=list) 的 taskId>)`。这是零 exec 约束下唯一合法的终止方式（不 exec kill 进程；cancel 在 coordinator_only 白名单内，且工具层硬限制只能取消主控自己 spawn 的子代理树——见上方「会话管理原语作用域」段）。取消可能不完整（工具报 error 而非 clean success）——取消后必须再 `subagents(action=list)` 复核是否真停，未停则重试 cancel（幂等）。各角色卡/模板/硬卡阈值表中的「kill」均指此操作。

## 二十三、编排循环防空转（教训 #274，2026-08-19 ECS 实战）

> **背景**：T8→T5 交接点被 duplicate 完成事件打断，spawn T5 的 tool call 丢失，主控空转 2.5 小时。根因：push-based 编排循环过度依赖「完成事件恰好投递一次」。

**主控在 T 角色交接点必须遵守的三道防御**（详见 [`_shared/执行韧化协议-exec.md`](../_shared/执行韧化协议-exec.md) § 4）：

1. **spawn 后立即验证落地**：每次 `sessions_spawn` 后用 `subagents(action=list)` 确认 runId 在 active，没出现 = spawn 丢失，立即重试（≤2 次）
2. **yield watchdog**：`yield` **会结束当前 turn**，完成事件只能作为下一条 message 到达——**不可在同 turn 内循环等**；若未收到预期完成事件 → **仅一次** on-demand 自查 `subagents(action=list)`（**非循环、非轮询**），判断 spawn 丢失空转还是子代理真在跑
3. **完成事件幂等**：收到某角色完成事件时先查 `status.md` 该角色是否已 Done，已 Done = duplicate 事件，**忽略不重复推进**
4. **交接点「三段式 spawn」**：T8→T5、T4→T8、T5→T4（修订）禁止「spawn → 直接 yield」，必须「spawn → 验证落地 → 确认后 yield」

**spawn 传参规范（taskName）**：`sessions_spawn` 的 `taskName` 参数须匹配 `[a-z][a-z0-9_-]{0,63}`（**≤64 字符**），**禁止数字/符号开头**（如 `1-T1-文献检索` 会被拒），且**不得使用保留字 `last` / `all`**（有控制含义）。命名建议：`t1-文献检索` / `t5-写手` / `t6-批判` 这类「字母前缀 + 角色」格式，便于 `subagents(action=list)` 与 status.md 对齐。

**主控 spawn 验证落地伪代码**：
```python
run = sessions_spawn(task=...)
if not subagents_has_active(run.runId):
    log("[#274] spawn runId={} 未落地，重试".format(run.runId))
    run = sessions_spawn(task=...)
```

**完成事件幂等伪代码**：
```python
def on_completion(role, runId):
    if status_md[role]['state'] == 'Done':
        log("[#274 幂等] {} 已在 Done，忽略 duplicate runId={}".format(role, runId))
        return
    status_md[role]['state'] = 'Done'
    spawn_next_role()
```

2. **优先磁盘**：先 `read` 该角色产物文件——产物完整 → **直接采纳**（截断只是回传层现象，磁盘产物不受影响）

3. 主控在 status.md 终检段写明 `[archive HH:MM] 按 {strategy} 产出保留清单，建议保留 N 文件，建议清理 M 文件`
4. **agent 在任何阶段都不执行删除**（零 exec + 防误删红线）——主控只产出清单，删除动作由主人在 host shell 手动执行

**实战背景**：v1/v2/v3 + 修订说明 ×3 = ~100KB archive/，按 keep_last_2 策略只需保留 v2 + v3 = ~30KB。

**为什么不由 agent 执行**：
- 反哺报告不自动 commit = 主人 review 原则
- 清理 archive 也按同样原则——主控只产清单，主人决策后自行在 host shell 执行
- 论衡零 exec 是硬边界，不存在「升级为自动执行」的选项

## 二十六、T9 扩写/改写清单承接协议（教训 #168）

T9 跑完后主控必询问主人 3 选项（主人《论艺术中的丑》反馈）：

```
## T9 评审完成 + 主人决策

T9 总评分：XX/30
建议：accept / minor / major / reject
目标期刊适配：《XX》（匹配度 X%）
扩写/改写清单：见 audits/审稿报告-v{N}.md 末段

**主人决策**：
- □ A. 接受现状定稿，投稿（不修订，Phase 5 终检直接交付）
- □ B. 触发扩写修订（**B 类修订，不占用常规 2 轮预算（登记，见仲裁表）**，主控 spawn T5 v4 写手，prompt 附 T9 扩写清单作为任务书）
- □ C. 换期刊（字数匹配 5000 字，选其他期刊）
- □ D. 主人明示其他调整

**触发 B 类修订**（主控确认后）：
1. 主控读 T9 报告末段「扩写/改写清单」
2. 主控同步修改任务简报「目标篇幅」字段（如果扩写）
3. 主控 spawn T5 v4 写手，prompt 显式附：
   - 「基于 drafts/初稿-v{N}.md 扩写」
   - 「目标期刊要求：XXX」
   - 「扩写清单：...（逐条）」
4. T5 v4 完成后 → T7 审计 → T8 终检 → 主人最终验收

**为什么不自动触发**：
- 反哺报告不自动 commit = 主人 review 原则
- T9 扩写建议也按同样原则——主控列出建议，主人决策
- 实战中 T9 建议可能与主人战略冲突（如不想投稿该期刊、不想扩写）
- 主控不替主人做战略决策
```

**实战背景**：主人《论艺术中的丑》T9 建议「投《文艺研究》需扩写 8000+ 字」，但字数在 Phase 0 定死 = 5000 字 → T9 建议无处承接。T9 输出「扩写清单」+ 主控决策 B 类修订。

**B 类修订与 ≤2 轮的关系**（教训 #283）：
- A 类（T7 打回结构性 P0/P1）→ 计入 ≤2 轮
- B 类（主人决策触发，包括字数压缩/扩写/换期刊）→ **不占用常规 2 轮预算（登记，见仲裁表）**
- C 类（T8 亲修 P1-D 事实错误）→ 不占用常规 2 轮预算（登记，见仲裁表）

主控在 spawn T5 v4 时 prompt 显式标「[B 类修订触发 = 主人决策扩写]」+ status.md 修订回环记录「**B 类 v4 主控触发扩写**」。
