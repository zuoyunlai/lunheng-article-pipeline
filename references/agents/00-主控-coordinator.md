## 「据行业经验估算」限定使用条件（v2.1.1 新增，教训 #44，回应 ClawHub 92% finding）

> 背景：v2.0.7 主控洞察融合协议允许使用「据行业经验估算」软化未源化数字。但 ClawHub 安全审计指出这会成为「hedging language loophole」—— agent 可随意用该措辞让未经验证数据通过审计。

**限定使用条件**（满足**全部**才能使用）：
1. **三源检索全失败**：① T1 文献检索 + ② T2 数据检索 + ③ web_search 补充均**未找到任何可引用的数字**
2. **段落顶部加注**：每次使用前在该段落开头写明 `[行业估算，非数据卡]` 标记
3. **附估算依据**：该数字必须能基于「业内常识」「从业者经验」「结构性推理」之一推导（不能凭空出现）
4. **不超过全文 3 处**：全文章「据行业经验估算」类措辞累计 ≤3 处（防止滥用）
5. **T7 审计必查 G2.5 估算标记（v2.3.0 改 T5→T7）**：T7 在 G2 数据溯源里加一条专门查估算使用频次，超过 3 处 → P1

**禁止使用的场景**：
- ❌「据行业经验估算」+ 具体百分比/元数（更精确 = 更需数据卡）
- ❌ 同一论点同时使用数据卡数字 + 估算（混用 = 不可验证）
- ❌ 全文结论性数字（必须可溯源）

**示例**：
- ✅ 正确：开模打样成本「据行业经验估算」动辄「数十万元」（有范围、无精确值）
- ❌ 错误：开模打样成本「据行业经验估算」47 万元/ SKU（伪装精确度）
- ❌ 错误：同一段同时使用 D15（顾家 184.8 亿）+ 估算数字（数据混用）
- 写手收到含主人洞察的指令时，按本协议做转换；如拿不准，**默认 A 档客观化**

## 主控状态汇报粒度（v2.2.10 新增，v2.3.7 增强，教训 #107 + #133）

> **背景**：v2.2.10 初版做「阶段级汇报」护主人不被打断，但实战发现阶段太长（Phase 1 检索 10-15 分钟），主人不知道角色是否在工作、卡住也得不到反馈。v2.3.7 增强为「派发 + 完成节点汇报 + 卡住保活」，既不打搅主人，又让主人随时知道进度。

- **派发节点汇报**（v2.3.7 新增）：主控 spawn 每个角色**前**，主动发一条：「📋 Phase N：派发 <角色>（<模型>），预计 <耗时>」。让主人知道流水线正在启动、每个阶段开始了。
- **完成节点汇报**（v2.3.7 新增）：主控收到每个角色完成报告并**验证产物后**，主动发一条：「✅ <角色> 完成：<产物摘要>（N 篇文献 / M 条数据 / K 个案例）」。让主人知道进度在推进。
- **阶段汇总汇报**（保留 v2.2.10）：Phase 内所有 T 完成后，补一条阶段汇总（含下阶段状态 + 产物路径）。
- **卡住保活告警**（v2.3.7 新增）：
  - 角色超过预计时间 50% 未完成 → 主动发「⏳ <角色> 已超预计时间，仍在进行，继续等待」
  - 角色静默（>8 分钟无心跳/无产出）→ 立即告警「⚠️ <角色> 静默超时，触发 <兜底>」并介入（沿用「主动介入机制」6 步）
- **异常即时打断**（保留 v2.2.10）：角色中途出错 / 产物异常 / 跳过质控阈值 / 需主人在环决策 → 立即报告，不等阶段完成
- **预计状态汇总**（保留）：status.md 顶部维护「当前 Phase 进度条」，主人可随时查
- **汇报原则**：① 每条 ≤2-3 行，不刷屏 ② 派发/完成/异常必报，中间心跳不打扰 ③ 卡住时宁可多报「仍在进行」也不让主人干等

### 状态汇报协议伪代码
```python
# 派发节点
on_spawn(t_role):
    msg(f"📋 Phase {phase}: 派发 {t_role}（{model}），预计 {eta}")

# 完成节点（验证产物后）
on_complete(t_role, artifact):
    verify_artifact(artifact)  # 完成验证铁律
    msg(f"✅ {t_role} 完成：{summary(artifact)}")

# 卡住保活
if elapsed > eta * 1.5:
    msg(f"⏳ {t_role} 已超预计时间，仍在进行")
if silent > 8min:
    msg(f"⚠️ {t_role} 静默超时，触发兜底")
    intervene()  # 主动介入机制 6 步

# 阶段汇总
if phase_complete:
    msg(f"[{phase}] {summary} → 产物: {artifacts}")
```

## 主动介入机制（v2.1.0 6 步，含 F4 轮次约束）

发现下游角色卡住（静默 >8 分钟或无产出）→ 主动介入：
1. 查 status.md 是否含心跳/ack（缺失 = 没遵循 v2.1.0 协议 → 拍醒子代理）
2. 用 sessions_history 看子代理最近输出（判断是真卡还是模型思考中）
3. 如果模型健康度问题 → 手动 kill 会话，手动 spawn 新子代理（指定下一档 fallback 模型）
4. 如果只是产生物到中途中断（partial output 存在）→ 接受现有产出，手动补齐缺失部分
5. 在 status.md 阶段行写明介入记录：`[介入 HH:MM] 主控介入，xession-kill，重派 model=fallback1`
6. **两类上限独立判断**（F4 重构 + v2.2.0 补强）：
   - **同场景重试 ≤2 次**（重派同一任务），避免无限重试
   - **修订回环 ≤2 轮硬约束**（**T7** 审计打回后 **T5** 重写，v2.3.0 改 T5→T7/T4→T5，**v2.2.0 新增，教训 #64**；**v2.3.1 定义细化 + T8 小幅修补权限 + P1 分级，教训 #120**；**v2.3.7 论文三实战升级（P1-3）二分类修订**，详见 deliverables.md「修订回环」）：
7. **并发子代理文件覆盖防护（v2.3.2 新增，教训 #126）**：主控兜底派发 fallback 前，**必须先查主任务是否还在产出**，避免两份产物对同一文件二次覆盖：
   - **fallback 派发前置检查**：`stat -c %y <文件>` 看 mtime 与当前时间差，若 <2 分钟（说明主任务刚写盘还在跑）→ **不派 fallback**，再等主任务
   - **命名隔离**：同一角色多份并行时，用 `<文件>.<模型>.md` 命名隔离（如 `06-v2-attack.deepseek-v4-pro.md`），禁止两份同写一个文件名
   - **硬卡放宽（教训 #126 + #131）**：T6 批判/T7 审计 12-15 分钟（"批判+修订"任务需更长）；T1-T3 检索 10-12 分钟（中文检索单次 7s+）；旧 8 分钟硬卡对这两类任务偏紧，导致「主任务其实写好了但被误判超时 → fallback 覆盖」

## 编排循环防空转（v2.2.8 新增，教训 #102，2026-08-19 ECS 实战）

> **背景**：T8→T5 交接点被 duplicate 完成事件打断，spawn T5 的 tool call 丢失，主控空转 2.5 小时。根因：push-based 编排循环过度依赖「完成事件恰好投递一次」。

**主控在 T 角色交接点必须遵守的三道防御**（详见 [`_shared/执行韧化协议-v2.1.0.md`](../_shared/执行韧化协议-v2.1.0.md) § 4）：

1. **spawn 后立即验证落地**：每次 `sessions_spawn` 后用 `subagents(action=list)` 确认 runId 在 active，没出现 = spawn 丢失，立即重试（≤2 次）
2. **yield watchdog**：yield 后 3 分钟无完成事件 → 自查 `subagents list` + `sessions_list`，判断 spawn 丢失空转还是子代理真在跑
3. **完成事件幂等**：收到某角色完成事件时先查 `status.md` 该角色是否已 Done，已 Done = duplicate 事件，**忽略不重复推进**
4. **交接点「三段式 spawn」**：T8→T5、T4→T8、T5→T4（修订）禁止「spawn → 直接 yield」，必须「spawn → 验证落地 → 确认后 yield」

**主控 spawn 验证落地伪代码**：
```python
run = sessions_spawn(task=...)
if not subagents_has_active(run.runId):
    log("[#102] spawn runId={} 未落地，重试".format(run.runId))
    run = sessions_spawn(task=...)
```

**完成事件幂等伪代码**：
```python
def on_completion(role, runId):
    if status_md[role]['state'] == 'Done':
        log("[#102 幂等] {} 已在 Done，忽略 duplicate runId={}".format(role, runId))
        return
    status_md[role]['state'] = 'Done'
    spawn_next_role()
```

**诊断（spawn 链空转排查）**：

```bash
grep -oE 'session_key: agent:[a-z]+:subagent:[a-f0-9-]+' $F | sort | uniq -c | sort -rn | head -5
# 同一 subagent uuid >1 次 = duplicate 完成事件
```
