## 三、工作流程（Phase 0-5 共 6 个阶段：Phase 0 定题 + Phase 1-5 主流程）

### Phase 0 定题（主控 × 人类）
- 4 选 1 同意关卡（全部同意 / 脱敏+本地 / 部分同意 / 全部拒绝）
- 主人确认主题/类型/篇幅/引用格式/deadline

### Phase 1 并行检索（T1∥T2∥T3 三方真并行）
- T1 文献 + T2 数据 + T3 案例（含 0 条场景走空卡协议）

### Phase 2 分析（T4）
- 三角验证：[L] + [D] + [C]
- 反方论证规划 + 原创性声明

### Phase 2.5 大纲确认（人在环）
- 主人过目分析大纲

### Phase 3 写作（T5）
- 初稿 v1 → 修订（**Phase 3.6/3.7 批判修订** / **Phase 4.2 审计修订**）；轮次映射与判定 → 见 `_shared/pipeline-overview.md`『修订回环仲裁规则』（单一真源；本文件不复述轮次数字）
- AI 去味 10 项 + 反方论证

### Phase 3.5 洞察补充（人在环）
- 主控向主人呈现初稿 v1
- 主人明确选择：补充深度洞察，或「无补充」；两者都写入项目状态
- 只有在有洞察时，T5 写手才产出 v2；「无补充」不是静默跳过
- 随后进入 Phase 3.6，由 T6 批判伙伴产出 `analysis/批判报告-vN.md`

### Phase 4 审计（T7）
- M 门+ G 清单（G0-G14）+ F 失败模式（F1-F9）
- 修订任务书（如打回）

### Phase 4.4 前置 G14 痕迹闸（`g14_style_gate`）
- **G14 中文 AI 痕迹闸**：定稿前最后一道闸，**全流程只审一次（不再复检）**；8 类检测维度，LLM 推理判定（零 exec），0-2 类 Pass / 3-4 类 Warning（呈报 3 选 1）/ 5+ 类 Fail → 由 T5 做最后一次风格层修订（`t5_style_revision`）
- 位置真源 = `_shared/phase-order.yaml`；八类判定真源 = `gates/14-中文AI痕迹-gate.md`（本文件不复述八类明细）

### Phase 4.5 同行评审（T9）
- **T9 同行评审**（按模式触发）：行业分析/学术论文默认开启，公众号可选关闭；模拟期刊审稿人 6 维度评分 → accept/minor/major/reject 建议
- **方法论实时可见面板**：status.md 加「方法论足迹」段（当前阶段/证据强度/已触发闸门/下一步预测/不确定性/模型健康度），主人实时看清进度

### Phase 5 终检（T8 主控亲完成不 spawn，人在环）
- 证据包完整性 + 引用一致性 + AI 使用披露
- 主控向主人呈现 `final/定稿.md` + `交付说明.md`
- 主人明确选择接受、补改、重走某阶段或延期；未留下决策记录不得标记项目完成

**M 门渐进式执行**（分批触发，P0 错误提前暴露；**各项的项数与闸门步数一律以 `_shared/M-Gate-Algorithm.md` 伪代码为准，本文件不复述**）：
- Phase 1.5（T1/T2/T3 完成后）：T2.5 完整性门（M-Integrity-1 + M-Form-6）
- Phase 2.5（T4 分析后）：M-Form-3
- Phase 3.5（T5 v1 后，主人洞察）：M-Form-1/2/4/5
- Phase 3.6（T6 批判后）：M-Form-7 论证强度
- T7.5（T7 审计后）：M-Exist-1/2/3 + M-Integrity-2（完整性门）
- Phase 5（T8 终检）：按 M-Gate 真源跑 **T8 兜底集**（项数以 `_shared/M-Gate-Algorithm.md` 为准，本文件不复述）

（P0 错误提前暴露，详见 `_shared/M-Gate-Algorithm.md` M-Form / M-Exist / M-Integrity 各阶段描述；该文档为 🟠 分片必读——伪代码段必读，附录按需）

### 版本升级自审门（自指原则）
论衡**自身**版本升级时，用审别人的标准审自己——防「改 A 漏 B」。当前权威自审门 = 硬门三件套 + 内容质量门脚本（见下）。

### 修订后必跑硬门三件套（教训 #249）

**任何版本修订（含改 SKILL.md frontmatter `version:` 字段）完成后，在 commit 前必须依次跑硬门三件套**，三件套全过才算「修订完成」，不是「改完文件就算完成」：

1. **`./scripts/sync-version.sh`** —— 从 SKILL.md frontmatter 读版本号，批量同步到 69 个应含版本号的文件顶部（自动调用 self-audit-gate.sh 自审门（**以脚本实跑为准**：改动前务必重跑，勿引用历史数字））
2. **`./scripts/check-version.sh`** —— 只读验证 69 文件版本戳一致性（69 个应含版本号的文件全过才 exit 0）
3. **`./scripts/self-audit-gate.sh`** —— 全门自审（门 H 教训编号差集含裸 #N 格式；门 S 流程图可达性与入参链；门 T 权限口径一致性）

> **教训 #249 根因**：v2.11.1 内容修订写完后主控以为「完成」，未跑 sync-version.sh，导致 69 文件版本戳停在 v2.11.0、check-version.sh 报 52 缺失、门 H 漏检 #245（只扫「教训 #N」字面，扫不到教训索引表格裸 `| #N |` 格式）。**机械化硬门是纯被动的，不强制触发 = 形同虚设。**

### 修订后必跑内容质量门脚本（教训 #252，+ #253）

**新增「内容质量门脚本」作为硬门三件套的第四件**——任何内容质量 SOP 修订（含加「可发表性 6 维度」、增「国标引用顺序编码验证器」、改「图表完整性判据」等）后，在 commit 前必须额外跑：

4. **`./scripts/paper-ready-check.sh <项目名>`** —— 本地开发者脚本，跑项目定稿的 48 项可发表性检查（分组见 `可发表性判定表.md` 真源）

**运行时机**：实战项目进入 T8 终检前主控亲跑 + 修订 SOP 后用最近一个实战项目回归测一遍（如《网络女权主义与舆论生态》《工具调用能力的伦理边界》）——保证新机制不破坏既有项目交付标准。

**使用者侧执行**：本脚本仅维护者本机使用，不随发布包分发。使用者侧由 LLM 按可发表性判定表口诀推理执行同一规则，判据完全一致。

> **教训 #252 根因**：v2.11.1 散文补丁让 SKILL.md SOP 段 / 08 终检卡 / dispatch/T8 三处都新增了「可发表性」22 项判据，但都是给人读的散文，不是机器可执行——v2.12.0 实战回测《网络女权主义与舆论生态》立刻发现 6 项真实质量门缺失（前置要素 / AI 声明 / 类型标识 / 图表 / 致谢 / M 门），证明 exec 层保障才能打破「假绿灯反模式」。教训 #253 落地架构修订 = 判据单源 + 脚本化 + 双视图同步。

### 发版前置闸「两查一停」（教训 #332）

**任何对外发版动作（`git push` / `git tag` / GitHub Release / 净化包）之前，必须先过发版前置闸**——版本号、tag、远端 master、净化包目录都是**单点共享资源**，多条会话链并行修订时，「先发我的、让后来者再补」在版本谱系上不可交换（后发版本会落在落后的远端基线上）。

```bash
LUNHENG_PREFLIGHT_SELF_SESSION=<本链会话 key> bash scripts/release-preflight.sh <tag>
# 或 make preflight（需先 export LUNHENG_PREFLIGHT_SELF_SESSION）
```

| 查 | 判据 | 不过的处置 |
|---|---|---|
| ① 在飞链 | 同项目（`spawnedCwd` 在本仓内或 label/cwd 命中「论衡 / lunheng」）且 `status=running` 的会话 / 子会话数 = 0 | 退出码 10：等这些链 `done` 后重跑；本链自身用 `--self-session` 排除；确认是快照滞后的幽灵 running 才可 `--exclude`（会打印在报告里） |
| ② 编号占用 | 目标 tag 本地（`git tag -l`）与远端（`git ls-remote --tags`）均未占用 | 退出码 11：换号（编号不可复用，tag/Release 先后关系会与内容错位） |
| ③ 工作区干净 | `git status --porcelain` 为空（未跟踪文件默认同样计入） | 退出码 12：等改动链收口并提交，或先清理 |

- **通过时打印四行现状**（远端 master / 本地 HEAD / tag 区间 / 在飞链=0）——一眼看出谱系是否对齐（本地是否领先远端、有无本地独有 tag）。
- **闸只读**：不 push / 不打 tag / 不建 Release / 不改任何 ref，是「拒绝器」不是「执行器」；通过后仍由主人按 SOP 手工发版。
- **已挂进发版写路径**：`scripts/create-github-release.sh` 在**建 / 改 Release 前**强制调用本闸，未过则拒绝执行并透传退出码（10/11/12）；`--dry-run` / `--check` 为只读路径不进闸；`--skip-preflight` 是「已确认无并发链」的补救旁路（打印醒目警告）。
- **为何不挂 `sync-version.sh` 入口**：升版号本身常在「工作区不净」时才被触发（sync 就是用来收拾那棵树），挂上去会自锁；版本纪律靠本节 SOP + `create-github-release.sh` 的写路径闸落地。
- 回归测试：`tests/test_release_preflight.py`（21 项，零网络零 gh，用 fake ls-remote + fake 在飞链清单跑通「有在飞链 ⇒ 拒绝」「编号被占 ⇒ 拒绝」「全干净 ⇒ 通过」「放松模式放行/仍拒」）+ `tests/test_create_release_e2e.py`（6 项**端到端**：temp 仓库 + fake `gh`，断言「打 tag → `create-github-release.sh`」退出 0）。

#### 两个调用点：tag 前 vs tag 后补发 Release（教训 #334，v2.12.22）

**② 的「编号占用」口径只在「分配新号之前」成立。** `create-github-release.sh` 第 2 步铁律是「本地必须先有 tag」（先 tag、后建 Release），走它时号**必然已分配**；若闸仍按 ② 判，就是**闸与调用点时序语义错配**——正常发版路径被自己的闸拦死（实测补发 v2.12.19：`❌ 目标编号已被占用` → `EXIT=11`，Release 未创建，只剩 `--skip-preflight` 能走通，而该开关明文「不得作为常规发版路径」）。

故闸新增 `--allow-existing-tag`（**默认关闭**，严格口径完全不变），把 ② 细化为「编号是否被**本链之外**的人占用」，**仅当同时满足**才放行：

1. 该 tag 指向的 commit 属本链历史——= 待发布提交（默认 `HEAD`，可用 `--expect-commit <rev>` 改写）本身或**其祖先**（后者覆盖「发版后又补了 changelog 提交」的 v2.12.16 同型情形）；
2. 远端同号（若有）指向**同一对象**（annotated tag 按 `^{}` 解引用比对 commit）。

其余情形一律拒绝，**失败关闭**：tag 不在本链历史上（另一条链建的号）⇒ 11；远端同号不同对象 ⇒ 11；本地无 tag 而远端有（归属无法核验）⇒ 11；远端查不到 ⇒ 2。放松生效时报告首行打印醒目提示，不静默。

| 调用点 | 命令 |
|---|---|
| **tag 之前**（分配新号，Makefile / 手工 SOP） | `bash scripts/release-preflight.sh <tag>`（默认严格口径） |
| **tag 之后**（补发 / 同步 Release，写路径） | `bash scripts/create-github-release.sh <tag>` —— 内部自动带 `--allow-existing-tag` 调闸，无需手写 |
| **补发旧版 Release**（tag 不在 HEAD 历史上） | 手工调闸加 `--expect-commit <该版本提交>`；确认无并发链的补救场景才用 `create-github-release.sh --skip-preflight` |

> **通用原则（教训 #334）**：新增拒绝式闸门后，**立即端到端跑一次它本该放行的主路径**——否则会造出「上线即自锁」的闸。门类改动必须配「应当放行」的正向样本，不能只测「应当拒绝」。
