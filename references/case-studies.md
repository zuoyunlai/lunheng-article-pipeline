## 案例 1：商业热点深度文

### 项目概况

- **类型**：商业评论（事件驱动型深度长文）
- **规模**：8 节 / 7650 字 / 2 数据图 / 52 文献 / 60 数据点
- **耗时**：全流程约 2 小时
- **论衡版本**：v2.0.x

### 关键产出

- **事件时间线修正**：「三次炮轰」实为「两年五次」——主动检索发现媒体广泛传播的时间线有误
- **监管规则逐条对照**：把行业核心规则（机构监管/平台监管/舆论监管）逐条梳理
- **行业案例对比**：横向对比同类企业处理方式，给出坐标系

### 实战教训

- **受众默认按普通人写，不硬贴作者职业视角**——除非作者明确要求，否则不要假设读者是同行；本文读者是普通商业读者，不预设行业知识
- **事件时间线必须主动核查**——媒体口径可能与原始公告有时间线偏差（如「三次炮轰」实为「五次」），不能直接引用二手报道
- **监管规则逐条对照是这类文章的杀手锏**——比泛泛「受监管影响」有说服力得多

## 案例 2：品牌一致性深度文

### 项目概况

- **类型**：行业分析（多案例对比型）
- **规模**：~7900 字 / 15 文献 / 54 数据点
- **耗时**：约 3 小时（含修订 2 轮）
- **论衡版本**：v2.1.x

### 关键产出

- 5 个品牌案例横向对比（JCPenney / MUJI / IKEA / 主公品牌 / 主公品牌）——纵贯 10 年品牌战略变化
- 8 项 P0/P1 审计发现全部修复（教训 #265，sed -i 静默清空文件事故已沉淀）

### 实战教训

- **修订后复核环节在主控会话外无人值守时易卡住**——主控 spawn 写手修订 → 写手完成后没主动叫主控复核 → 主控在等写手 ack 时空转。解法：写手交稿前必须主动 ping 主控确认收到
- **失败案例需独立案例卡格式**——之前失败案例（JCPenney/MUJI/宜家）作为数据点存在但缺独立案例卡格式 → v2.1 优化为案例卡单独立档
- **多案例对比型文章证据底座要按案例分卡**——不要把所有案例混在数据卡里，案例独立成卡可被多次复用

## 案例 3：原创性悖论深度文

### 项目概况

- **类型**：行业分析（原创性概念首发）
- **规模**：~9500 字 / 12 文献 / 34 数据 / 6 案例
- **耗时**：约 4 小时（含 4 轮修订）
- **论衡版本**：v2.2 + v2.3 首次实战

### 关键产出

- 原创概念「原创性悖论」首发：抄袭成本低/维权成本高/品牌溢价无法兑现的三重错位
- 全文 4 轮修订：v1 主控精修 → v2 主人亲调 P5/P6 → v3 二次审计修 1P1+3P2 → v4 终稿
- A- 评级（实战项目质量评级）

### 实战教训（3 类修复的源头）

| # | 问题 | 现象 | 解法 |
|---|------|------|-----------------|
| ① | T3 三连超时 | 分析员调度超时，主控反复 spawn | 加调度模型健康度预检 + 超时硬卡 8 分钟 |
| ② | 主人亲历「我接触过」+「10-50 万/SKU」无源 | 写手代入了主体声音 | 加写手视角一致性铁律+ 审计 G0.5 |
| ③ | 图注「维权前后 9 年」精度不足 | 图注时间起点终点模糊 | 加图注时间三要素铁律（起点+终点+时长） |

### 论衡机制升级

- **主人深度洞察融合协议（3 档处理）**：观点来源 vs 理论贡献 分类标注
- **反哺报告机制**：强制默认只产出，不自动 commit 角色卡
- **论据类型自标 G6**：每个论据段落标 `（数据基础）` / `（案例支撑）` / `（主人结构性观察）` / `（业内常识）` / `（反方论证）`，让读者判断可信度

## 案例 5：AI 安全隐患

### 项目概况

- **类型**：行业分析（生成式 AI 安全议题）
- **规模**：~5700 字 / 52 数据 / 24 文献 / 5 案例
- **耗时**：约 3 小时（含 2 轮修订）
- **论衡版本**：v2.2.3（GLM-5.3 迁移后首次实战）

### 关键产出

- 主线 83.3%（>80% 预警 P1，主人决策不拆分）
- 2 轮修订全消化 P0/P1/P2

### 实战教训

- **T6 批判伙伴实测有效**——抓出「2020 年 2500 万」这处写手凭记忆写入的无主数据（实为 2019 €220k + 2024 Arup 混淆）。证据铁律「不得凭记忆写入未经素材核实的数字」再次验证
- **T7 独立审计价值**——spawn 独立审计子代理 + 规则化 M 门（read 比对），比自己复核更能抓漏引和元数据泄漏这类「自己看不见」的问题
- **补检索直接落证优于删除**——用真实 2019 英国能源公司深伪语音案替换「2020 年 2500 万案」，比「删除改写」更有信息量
- **修订必须先 cp v2 再改 v2**——v2.2.4 实战教训：主控改在 v1 上再复制成 v2 导致版本链混乱。正确顺序：`cp 初稿-v1.md 初稿-v2.md` → 在 v2 上 edit → v1 保持原始
- **机构名必须逐一核验（read 回查，不凭记忆）**——Securia/Secunia 均错，实为 Gartner（2025），数据员凭记忆写机构名是常见错误

## 实战项目目录约定

每个深度长文项目固定目录结构：

```
run/<项目名>/
├── 01-任务简报.md       # Phase 0 产出
├── status.md            # 状态机
├── literature/文献卡.md
├── data/数据卡.md
├── cases/案例卡.md
├── analysis/分析大纲.md
├── analysis/批判报告-vN.md
├── drafts/初稿-v1.md → v2.md → v3.md
├── drafts/修订说明-vN.md
├── audits/审计报告-vN.md
├── final/定稿.md
├── final/图件/
├── final/证据包/
└── final/交付说明.md
```

**实战项目状态查询**：`run/<项目名>/status.md` 当前状态字段（Inbox/Assigned/In Progress/Review/Done/Failed）。

**实战教训沉淀**：项目教训只写入项目本地 `run/<项目>/audit-lessons.md`（建议草稿，教训 #N+1 编号不可回收）。主控**不自动修改** `lessons.md`、本案例库或任何跨项目共享文件——沉淀草稿经主人 review 批准后由主人人工 merge，agent 不执行 merge；新案例追加同样走「项目内草稿 → 主人 review → 人工 merge」。
