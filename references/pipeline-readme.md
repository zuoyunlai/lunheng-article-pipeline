## 快速开始

```
1. 主控确认主题（Phase 0）→ 写 01-任务简报.md + 初始化 status.md
2. 主控决策案例检索强度（轻量/中量/重量），写入 status.md
3. 主控调度模型健康度预检（v2.3 新增，详见下节）→ 决定该次 T 派发用哪个模型
4. 并行 spawn 文献检索员 + 数据检索员（用下面的派发话术）
5. sessions_yield 等两者完成
6. spawn 分析员 → 分析大纲产出 → Phase 2.5 送主人确认 → 通过后 spawn 写手
7. spawn 审计员 → 审计不过 → 写手交修订说明 + 修订稿（≤2 轮）→ 终检交付（含证据包）
```

## 调度模型健康度预检（v2.3 新增，教训 #35）

> 实战中 T3 连续 3 个模型（deepseek-v4-pro / minimax-m3 / claude-opus-5）全部超时，论衡主控亲自产出大纲。本机制旨在预判 + 降级 + 硬卡超时。

**主控 T 派发前必须执行 3 步**：

1. **健康度预检**（避免一上来派发到已知慢模型）：
   - deepseek-v4-flash：轻量检索默认，置信度高
   - deepseek-v4-pro：推理/分析默认，但有过超时历史（教训 #35）
   - minimax-m3：推理/分析 fallback，但近期 T3 三连超时主要责任方
   - claude-opus-5：审计顶配，但成本高
   - **主控派发前查 status.md 顶部「论衡本轮可用模型」表**（论衡会话启动时自动填）

2. **超时硬卡 8 分钟**（实战中旧阈值过宽，介入太晚）：
   - T 派发后 8 分钟内未出产物 → 判定超时，主控介入
   - 不允许「静默等 10 分钟」

3. **主控兜底产物明确标注**（v2.0 机制没标 → 写手不知道这是主控产物不是 T 产物）：
   - 任何 T 阶段主控亲自产出 → 必须在文件头标注「主控兜底 v1.0」+ 注明失败原因
   - 写手收到时能识别这是非 T 产物，调整引用对齐策略

## 流水线全景

```
Phase 0 定题       主人确认主题/期刊模板/篇幅 → 01-任务简报.md + status.md
Phase 1 并行检索   T1 文献检索员(文献卡A/B/C分级) ∥ T2 数据检索员(数据卡🟢🟡🔴+冲突并列 + v2.2 顺带案例卡)
                ∥ [可选] T6 案例检索员(cases/案例卡.md,重量场景才 spawn,2026-08-13 v2.2 新增)
Phase 2 分析       T3 分析员 → 分析大纲.md（论点-论据映射 + 反方论证 + v2.2 三角验证标注）
Phase 2.5 大纲确认 主人过目大纲 → 确认/修改（人在环，改方向成本最低）；主控把关三角验证（[L]+[D]+[C]）
Phase 3 写作       T4 写手 → 初稿-v1.md（禁做清单 + 反方论证 + 字数预算；引用标[Lxx]/数字标[Dxx]/案例标[Cxx]；修订 v2/v3 显式覆盖同路径）
Phase 4 审计       T5 审计员 → 审计报告（G0覆盖度/G1分级核验/G2溯源/G2.5案例核验/G3逻辑/G4格式/G5规范）
Phase 4.2 修订     写手交 修订说明 + 修订稿 → 审计员复核 → 最多 2 轮 → 仍不过升级主控
Phase 4.5 配图     仅当简报「配图需求」非无：写手已在正文标 [图N] 图位 → 主控程序化生成数据图表（数字与数据卡/[Cxx] 一致）
Phase 5 终检      主控终检 → final/定稿.md + 图件/（如有）+ 证据包/(文献+数据+案例+审计) + 交付说明.md → 高频问题反哺报告（不自动 commit 角色卡 — v2.0.2）
```

## status.md 状态机（主控维护，角色交接时更新）

每个任务状态：`Inbox → Assigned → In Progress → Review → Done | Failed`
- 每个角色交接时必须更新 `status.md` 对应行
- 失败要留原因；任一行停留 >8 分钟无进展 → 主控介入（v2.3 从 10 分钟收紧为 8 分钟）
- 模板：`templates/status-template.md`

## 派发话术（主控复制即用）

### 文献检索员（并行①）

```
你是「文献检索员」。任务编号 T1。
项目目录：run/<项目名>/
任务简报：先读 01-任务简报.md；更新 status.md 对应行为 In Progress
任务：
1. 用 web_search / tavily_search 检索主题相关文献（中英文；知网/万方/Google Scholar/期刊官网/SSRN 等）
2. 产出 literature/文献卡.md：8-15 条核心文献，按子问题分组
3. 每条必须真实存在：作者、年份、标题、期刊/来源、DOI 或 URL、与本文的关联
4. 每条标可信度等级：A（核心期刊/权威机构）/ B（一般期刊/预印本）/ C（网络/二手转引）——C 级必须诚实标注
5. 参考文献条目按任务简报指定格式输出（默认 GB/T 7714），写手可直接粘贴
6. 严禁编造引用；检索不到就写「未检索到」，不许凑数
7. 交接报告六要素（含 status.md 更新）
8. **先行者检索（原创性保证，v2.4）**：主动搜「该主题是否已有公开深度文/论文写过类似核心论点」，产出 `literature/先行者清单.md`（每条含：文章标题/作者/来源/年份/URL + 核心论点 + 与本文的差异点）
```

### 数据检索员（并行②）

```
你是「数据检索员」。任务编号 T2。

任务简报：先读 01-任务简报.md；更新 status.md 对应行为 In Progress
任务：
1. 用 web_search / tavily_search 检索主题相关统计数据与实证材料（国家统计局/世界银行/CEIC/皮书/权威数据库）
2. 产出 data/数据卡.md：每个数据点含「数值 + 来源机构 + 年份 + URL」；按子问题分组
3. 每条标时效评级：🟢 ≤2年 / 🟡 2-5年 / 🔴 >5年（红级显著标注）
4. 同指标多来源矛盾 → 强制并列呈现 + 口径差异说明，不擅自二选一
5. 严禁编造数据；找不到精确数据就标注「缺口：建议人工查 XX 数据库」
6. 交接报告六要素（含 status.md 更新）

[v2.2 案例扩权 — 主控已在派发时根据简报勾选启用]
7. 如主控在派发话术中标注了「启用案例卡（轻/中量）」：
   a. 同时产出 cases/案例卡.md，按 templates/案例卡-template.md 格式
   b. 中文新闻源覆盖：tavily_search 用 include_domains 限定（财经/商业/行业垂类/官方公告）
   c. 每条案例 ≥2 个独立来源 + 时间锚点（检索截止+事件窗口）+ 多方立场并列
   d. 案例编号 [Cxx] 与数据卡 [Dxx] 互引
8. 中量案例（4-8 条）应在数据卡完成后将 40% 时间投入案例卡

[强相关性铁律 · 2026-08-13 教训 #34]
9. **每条材料必答「它支撑哪个论点」**——卡片「与本文的关联」字段必填，答不出不收
10. **数量封顶 [Dxx] 30-50 + [Cxx] 5-8**，全套 50-70 条封顶
11. **反向淘汰自查**（交付前必走）：逐条问「删掉它哪条论点会塌」，无影响→砍；案例卡特别查「是示例还是证据？是示例就降级为正文引用不进案例卡」

[论据类型自标 · v2.3 新增，教训 #35]
12. **写手规则**：写任何「结构段落」（非「引用段落」）时，在段落末尾自标论据来源类型：
    - `（数据基础：§XXX）` / `（案例支撑：[Cxx]）` / `（主人结构性观察）` / `（业内常识）` / `（反方论证）`
    - 示例：第一节末尾 `（数据基础型论证，无具体企业个案）`
13. **审计员必查项 G6**：结构段落未自标论据类型 → P1（读者无法判断可信度）
```

### 审计员

```
你是「审计员」。任务编号 T5。你的职责是找出写手自己看不到的问题。
项目目录：run/<项目名>/
先读：01-任务简报.md、analysis/分析大纲.md、drafts/初稿-vN.md、literature/文献卡.md、data/数据卡.md；更新 status.md
任务：产出 audits/审计报告-vN.md，按严重级列出问题：
- P0 致命（必须改）：编造引用/数据/案例、论点无据、论证链断裂、跑题（研究问题未回答）
- P1 严重（应当改）：格式不统一、数据缺溯源/红级数据未说明、AI 空话套话、反方观点缺失、案例单源未降级
- P2 建议：可优化项
必须执行：
0. G0 覆盖度：对照任务简报逐项核对每个研究问题是否被回答、有无跑题
1. G1 分级核验：C 级引用 100% 用 web_search 核验、B 级 ≥50%、A 级 ≥10%；抽到假的升级 P0 并全量核验；抽验时做上下文匹配检查（防张冠李戴）
2. G2 数据溯源：逐个数字找来源；数据卡没有的 → P0；关键论点用红级数据未说明 → P1
2.5. G2.5 案例核验（仅当存在 cases/案例卡.md）：每条 ≥2 来源不达标 → P1；缺检索截止日期 → P1；多方立场未并列 → P1；C 级案例当作 A 级用 → P0
3. G3 逻辑：对照大纲检查论点-论据映射是否成立；涉及企业行为/事件的论点是否有 [Cxx] 支撑 → 缺角 P1
4. G4 格式：结构完整、引用格式符合期刊模板、参考文献与正文标注一一对应、篇幅符合预算
5. G5 规范：查重意识 + 写手禁做清单 10 项逐项查
6. G7 原创性审计（v2.4）：对照先行者清单 + 分析大纲原创性声明，核验本文核心论点是否与公开文章重复；重复且未声明 → P0；差异点声明模糊/无实质差异 → P1
若本轮是修订稿：对照写手修订说明逐条确认 P0/P1 关闭情况，未关闭的升级 P0。
结尾给出结论：通过 / 打回修订（附必须修改清单）
交接报告六要素（含 status.md 更新）
```

- `final/图件/`（仅当简报「配图需求」非无）：扫描定稿 [图N] 图位生成的数据图表 + 封面视觉（如有）；图件与正文图位一一对应，数字与数据卡一致
- `final/证据包/`：文献卡 + 数据卡 + 审计报告 + 引用核验记录（供投稿/答辩前人工复核）

- 每单结束：审计高频问题 → 沉淀进 `agents/04-写作-writer.md` 禁做清单（自我改进闭环）

### 定稿引用规范（主人 2026-08-12 确立，水与麦单修正）
1. **正文必须带来源标注**：每个数据/观点后标 `（机构，年份）` 内联标注（公众号风格），或保留 [Dxx]/[Lxx] 编号并在文末附「引用来源」清单（编号→机构→年份→标题→URL）。**禁止把引用删成无标注裸文**——删掉引用即删掉可信度。
2. **文末引用清单**：`## 引用来源` 分「文献」「数据」两节，每条含编号+机构+年份+标题+URL；测算值/综合判断条目如实标注"测算值/综合判断"，不伪称有来源。
3. **编号残留检查**：交付前 grep `\[D\d+\]|\[L\d+\]` 清零，或全部转换为内联标注。

### PDF 生成规范（主控负责，水与麦单修正）
1. **字体必须先验证**：`fc-list :lang=zh` 检查系统实际字体（本机为 Noto Serif SC/微软雅黑/宋体），CSS 只写存在的字体；写不存在的字体名（如 Noto Serif CJK SC）会导致乱码。
2. **生成后必须验证**：用 pymupdf 提取首页文本抽查无乱码，检查页数与末页内容。
3. **版本另存**：PDF 每次修订重新生成前，旧版先另存版本号（如 `-v1.pdf`），不覆盖。

### 修订规范（教训 #11：改稿必先另存版本号）
- 任何「基于 X 版做修订」的任务，第一步 copy 出新版本号文件，再动笔；
- 定稿后主人的任何修改意见（标题/结构/引用）→ 先备份当前版（`定稿-完整版.md` 或 `-vN`），再改。
- 三处同步：论衡 run 目录 ↔ 主人 outputs 目录 ↔ PDF，修改后必须同步，防止版本漂移。

## 配图生成规范（Phase 4.5）

- **数据图表**：程序化生成（matplotlib/SVG 脚本），禁止文生图（数字不可控）。图位来自写手标注的 [图N]，图上数字必须与数据卡/正文 [Dxx]/案例卡 [Cxx] 一致，生成后抽查核对。
- **封面视觉**：默认调用 image_generate 工具生成（默认 **OpenAI gpt-image-2**，考虑普适性——任何装了 OpenAI key 的环境都能跑）；出图先送主人确认风格再定稿。如不可用或失败（按 recover_failed_article_illustration_gen 模式自动降级 fallback 顺序：Google gemini-3.1-flash-image-preview → minimax/minimax-image-01），仍失败则 fallback 到 SVG 矢量风（程序化生成）或主人人工上传到 final/图件/封面.png
- **案例示意图**（v2.2 可选）：复杂事件链可用 SVG 画时间线/关系图，不画文生图。
- **脚本复用**：参考 `outputs/` 既有图表脚本（如 russia_casualties.png 同款 matplotlib 流程、竹知了 SVG 矢量渲染流程），或本项目 `run/<项目名>/scripts/` 下已固化的工具。

## 模型配置与更换指南（v2.3）

> 本流水线的模型是**能力分层**，不是**模型锁定**。上表模型名是本机默认，任何 OpenClaw 兼容模型（OpenAI 兼容 API）都可替换。

### 三层模型配置（从外到内）

| 层 | 配置位置 | 更换方式 |
|----|---------|----------|
| **1. 主控 agent 本体** | OpenClaw 配置 `agents.list[<agent>].model` | `primary` 主模型 + `fallbacks` 降级列表，改配置后重启 gateway |
| **2. 各角色 spawn 模型** | `sessions_spawn` 的 `model` 参数 | 主控派发话术里直接指定每个 T 角色用哪个模型 |
| **3. 角色卡「模型建议」表** | 本 README「成本与模型建议」表 | 只作建议，实际 spawn 时以主控派发为准 |

### 更换的自由、途径、权限

- **自由**：检索/分析/写作/审计/主控每个角色都能独立换模型，按「能力分层」原则自由搭配
- **途径**：① 改 OpenClaw `openclaw.json` 的 `agents.list[<agent>].model` ② 改 `sessions_spawn` 的 `model` 参数 ③ 改角色卡「模型建议」表
- **权限**：任何有对应 provider 配置的 OpenClaw 兼容模型都能用，无需改流水线代码，只需改配置

### 能力分层原则（换模型时遵循）

| 角色 | 能力要求 | 选模型标准 |
|------|---------|-----------|
| 检索 | 便宜 + 快 | 低单价 + 短延迟，1M 上下文优先 |
| 分析/写作 | 强推理 + 中文长文 | 高质量中文输出 + 大上下文（证据包可达 50-70 条） |
| 审计 | 顶配 + 专抓错 | 最强模型，宁可贵不可漏 |
| 主控 | 判断 + 路由 | 强推理 + 稳定（避免频繁超时的模型） |
