## 二、修订项清单

> 严重度口径：**P0** = 会产生假绿灯或错误交付结论；**P1** = 契约自相矛盾/判据错误，主控可能照做；**P2** = 体验与度量缺口。

### P0 档

#### R-1｜Phase 1.5 触发条件依赖尚未产生的上游报告（时序自指）

- **证据**：`phase1_5_targeted_review.yaml` 位于 `phase_seq 4`，`t2_5_integrity` 位于 `phase_seq 5`；前者 `trigger_conditions` 含 `t2_5_red_data_unresolved`，且标 `rerun_after_report: true`。
- **问题**：首次到达 Phase 1.5 时 T2.5 尚未执行 ⇒ 该触发项**恒为假**；`on_not_triggered: record_not_triggered_in_status` 会把它记成"未触发"，与"漏跑"在留痕层不可分。
- **建议**（三选一，需拍板，见 §四·B）：
  - **B1 拆两个求值点**：保留 seq 4 为「简报标记窗口」（只看 `brief_marked_Dxx/Lxx_for_review`），新增 seq 5.5「T2.5 后置红数据窗口」（只看 `t2_5_red_data_unresolved`），二者共用 `t1b` 派发契约；
  - **B2 单节点双求值**：节点内声明 `evaluation_phases: [pre_t2_5, post_t2_5]`，两次求值各记 `evaluated_against`，第二次求值命中即 `after_trigger: rerun_t2_5_integrity`；
  - **B3 删该项**：Phase 1.5 只看简报标记，红数据统一交给 seq 15 的 `t1b_targeted_review`。
- **倾向**：B1（语义最清、留痕最干净），但会增加 1 个节点 ⇒ 触发 `counts.yaml: pipeline_nodes` + `pipeline-overview` 全景 + 装配视图重生成。
- **构建门影响**：`phase-order-slice.py` 重跑（门 AA）、`counts.yaml: pipeline_nodes`、`pipeline-overview.md` 全景表、可能的 `test_count_drift` 模式扩充。

#### R-2｜终态「已完成」缺对账门，status 内部可自相矛盾

- **证据**（2026-10-06 实跑 `status.md`）：头部写「已交付并通过 Phase 5 验收」「当前活动=完成」，同文件内 `Phase 3.5 洞察: decision=未决策`、`T7.5: ⬜ Inbox`、`T8 技术终检: ⬜ 未完成`、`status_json.updated_at=2026-10-07 15:18`（停在项目早期）、§4.1 仍写「Phase retrieval」、§4.7 token 表全「待记」。
- **问题**：`phase5_acceptance` 是唯一终态闸门，但其前置只校验"主人决策"，**不校验状态机自身一致性** ⇒ 头部/详情两套真相可长期并存而不报红。这是 v2.15.12 项目的执行证据，**不能直接判为 v2.15.13 再现**，但机制缺口在 v2.15.13 仍然存在。
- **建议**：
  1. 新增 `acceptance_reconciliation` 前置子判据（写进 `phase5_acceptance.yaml`）：四节点 `decision` 齐且非 `未决策/n/a`、全部必经报告在盘非空、`status_json.phase` 与 `closed` 同当前阶段一致；
  2. **治本项**：`status-template.md` 把「头部摘要」降级为**派生视图**（标注"以下字段由详情段生成，不得独立编辑"），真源收敛到详情段 + `status_json`；
  3. 新增回归门：反向注入「头部 `closed=true` + 详情段存在未完成节点」⇒ 必红。
- **构建门影响**：新增 flow-check 规则（须同批登记 `test_flow_check_meta.py` 的 COVERED/DEBT，`COVERED_MIN` 只许涨、总数 ≤50）、`status-template.md` 结构改写连带 B12 类规则。

#### R-3｜「可投稿」无阻断条件：形式门全过 ≠ 交付就绪

- **证据**（同一实跑）：`final/交付说明.md` 第四节 **D 国标引用 = ⚠️ 部分**（正文 `[L01]…[L15]` 三轨 vs 文末 `[1]–[15]` 单轨），第十二节列「投稿前引文体例统一」为**未随验收执行**项；`audits/审稿报告-v1.md` = **22/30、minor revision、desk_reject_risk=medium**，建议 2/3/4 未执行；交付说明第七节自承「轮 2 修订内容未经独立审计员复核」。
- **问题**：`v2.15.13` 已在 `可发表性判定表.md` 4.1 补入「正文标注体系 = 文末编号体系」与交付层映射要求（方向正确），但**没有把它接成 `phase5_acceptance` 的阻断判据** ⇒ 主人仍可在 D 项为 ⚠️ 时点「接受」，且「已接受」与「可投稿」在状态层无区分。
- **建议**：
  1. `phase5_acceptance` 增必呈现字段 `delivery_readiness: submission_ready | accepted_with_open_items`（**两者都要写，禁止留空**）；
  2. `submission_ready` 的必要条件（任一不满足即只能取 `accepted_with_open_items`）：可发表性 D 通过 + 无「待人工核验」著录残留 + 末轮 P0/P1 修订**经独立审计员复核**或已按 `rounds_exhausted_outlet` 记为未关闭项交主人裁决 + T9 建议已分流（采纳/记局限/记必做，三者必居其一）；
  3. 末轮修订的独立复核：若修订轮已耗尽且 T7 不可用，落 `unverified_by_independent_auditor` 显式状态（不静默），进 `submission_ready` 必要条件的否决项。
- **构建门影响**：若采纳为独立闸门 ⇒ 版本号按 `version_numbering.milestone_rule` 需**整数位推进**（见 §四·A）；`可发表性判定表.md` 判据数与 `counts.yaml: t8_*` 需复核是否新增项。

### P1 档

#### R-4｜`route_tier.md` 族数判据数学错误

- **证据**：§二 第 3 条写「**至少 2 个互异 provider 族**可用（满足 T6/T7/T9 三节点两两互异的最小池）」。
- **问题**：三节点两两互异需 **3 族**；2 族只能满足「每族最多 1 个独立节点」。实测 2026-10-06 正是 2 族（deepseek / minimax）⇒ T6 与 T9 同族，「模型独立性不成立」。按现文字主控会**误以为 2 族即可满足 T3 档探活通过**。
- **建议**：拆成两个可判定口径 —— `writer_audit_distinct_families: ≥2`（写手 vs 审计）与 `audit_full_independence_families: ≥3`（T6/T7/T9 两两互异）；探活分别记两档结论，探到 2 族时**当场告知主人**「仅满足前者」并把选项（接受部分同族 / 停摆 / 放宽）并入断路器三选一。

#### R-5｜Phase 0 路由「无记录 = 走默认链」与「主人选择」自相矛盾

- **证据**：`route_tier.md` §三 同时规定「Phase 0 弹选择、记录写 `phase0_route:` 段」与「**无记录 = 按 [1] 默认链执行并披露**」。
- **问题**：`checkpoint-card-template.md` 的 fail-closed 纪律是「静默 ≠ 决策」；此处却给"未询问/未记录"配了默认出口 ⇒ 漏呈现、漏记录与"主人主动选默认"三态不可分（与 R-2 同族病）。
- **建议**：删除「无记录走默认」；改为 `phase0_route` **缺记录 ⇒ 视同未过 Phase 0 后置**，`pre_spawn_enforcement` 判 `path_or_param_error` 并 halt 呈主人。选项 [1]「接受自动建议」保留为**必须被主人点击并记录**的显式项。

#### R-6｜`terminal_freeze` 重开顺序与 T9 输入依赖矛盾

- **证据**：`index.yaml: terminal_freeze.doctrine` 写「依次重跑 `g14_style_gate` / `t9_review` / `final_assembly` / `t8_technical_final`」；但 `t9_review.input = final/定稿.md`，且 `t9_review` 正常位序在 `final_assembly`（seq 20）**之后**。
- **问题**：按字面执行会在 T9 评审**旧版定稿**，重跑失去意义。
- **建议**：改为条件化重开链 —— `current_draft_sync`（若改稿）→ `g14_style_gate` → `phase4_4_figures`/`final_assembly`（含 `g14_caption_recheck`）→ `t9_review` → `t8_technical_final` → `phase5_acceptance` 重新取拍板。并在 `t9_review` 节点加断言：`audited_artifact` 三元组必须与重开后的 `final/定稿.md` 一致（已有 `audited_artifact_required` 字段可承）。

#### R-7｜`可发表性判定表.md` 判定伪代码与判据列不一致（主控可能照抄）

- **证据**：维度 5 判据列写「图件数 **= 拍板 N**」「正文引用数 **= 拍板 N**」，但同节 `check_charts()` 的 `passed = (svg_count >= 5 and body_ref_count >= 5 and ...)`；维度 4.3 判据写「正文引用顺序 = 文末列表顺序，双向无遗漏无错位」，但 `check_citation_ordering()` 的 `passed` 只判 `missing_in_appendix` 与 `unused_in_body` 是否为空，**从不比较顺序**。
- **问题**：主控是 LLM，会把伪代码当权威判据照搬 ⇒ ① 图件少于拍板数也能判过；② 引用**乱序**（`[3]` 在 `[1]` 之前）能判过。两者都是"形式门过但交付不合格"的假绿灯。
- **建议**：改伪代码使其与判据列严格一致（图位 = N 严格相等；顺序判据用 `body_unique_ordered == appendix_refs_ordered` 严格相等），并新增回归门：**反向注入「判据列 = N / 伪代码 = ≥5」必须报红**（防再次漂移）。

### P2 档

#### R-8｜上下文优化只有契约没有收益数据（B3 回归门退化为字段存在性检查）

- **证据**：`tests/test_b3_context_offload.py` 全部 5 个用例都是"某文件包含某 token"的断言；`current_draft_sync.context_metrics` 定义了 6 个指标，但 `performance-benchmarks.md` 无对应行。
- **建议**：新增**同稿对照实验**（非新增门，是一次性度量 + 登记）：取一篇已有长稿，分别用「全文重读」与「指针 + 局部读」完成同一 T7 判据任务，记录工具调用次数 / 墙钟 / 实际 token / `false_negative_count`；结果按现有 §二 表格加一行，结论决定是否收紧 `read_budget` 默认值。**样本 n=1，禁止外推为发生率**（沿用反哺报告 §〇 纪律）。

#### R-9｜`owner_checkpoint.blocks` 局部阻塞无机械门

- **证据**：`blocks:` 仅在 `index.yaml`（4 处）+ 4 个 owner_checkpoint 切片中声明；`test_flow_check.py` 现有规则 12 只校验 `blocking/owner_visible/decisions/timeout_fallback`，**未覆盖 `blocks`**。
- **问题**：FB-12 引入的局部阻塞语义无人守 ⇒ 后续有人删掉 `blocks` 会静默退回全局停摆（实跑中正是"主控自行并行"才没白等）。
- **建议**：flow-check 新增规则「4 个 owner_checkpoint 必须声明非空 `blocks`，且 `blocks` 引用的节点必须已定义」+ 1 条反向注入。

#### R-10｜`status.md` 头部摘要与详情段双份真相（同 R-2 的载体，单独记账）

- **证据**：实跑 status 的 §一 元数据、§4.1 当前阶段、§4.7 token 表、§4.9 `status_json` 四处都在描述"当前状态"，实测 §4.1 停在 Phase 1、`status_json` 停在 15:18，而 §二 已记到 Phase 5。
- **建议**：与 R-2② 合并施工；短期先加 `derived_fields: true` 标注 + 验收前对账，长期把四段压成一节。

#### R-11｜Checkpoint 卡在 Phase 0 叠加过多必答项

- **证据**：`checkpoint-card-template.md` Phase 0 必呈现 = 定题决策 + 外发 4 选 1 + 2 项功能可选项 + 模型映射披露 + 路由方案（route_tier §三）+ 文件清单确认 + `route_tier` 探活结果。
- **问题**：单卡 >6 个必答项时，主人实际只回前 1-2 项，其余静默 ⇒ 与 R-5 同源的"静默≠决策"漏洞（`ask_user` 适用性判据也把 Phase 0 排除在外，只剩纯文本）。
- **建议**：拆两层 —— 卡片首屏只放**唯一核心决策 + 2 个高影响项**，其余折叠为"已按默认设置，需改请说"（并明确标注"未回复 = 按记录值执行，这些是**已记录**不是**待决策**"），把"待决策"与"待确认"在卡上用不同标记区分。

#### R-12｜效率度量三缺口导致"运行效率"不可评

- **证据**：① 子代理 Stats line 连续 3 轮缺失（`performance-benchmarks.md` §二 三行 token 大量 `未捕获`）；② `sha256` / 精确 `bytes` 属主人侧量值，`current_draft.md` 的 `sha256_status` 在实跑中为 `unavailable` ⇒ 幂等探测与 `hash_mismatch` 分支**从未被真实执行过**；③ 主控上下文余量全程 `unavailable`（平台未给窗口值）。
- **建议**（均为"记录纪律"而非新门）：
  1. 主控在**每个节点完成时**固定采一次 `session_status`，把主控侧累计 token 逐点写入 §4.7（当前只有 1 个采样点）；
  2. 宿主若能提供窗口值则回填，否则保持 `unavailable`（**不伪造百分比**）；
  3. 首次项目请主人回填一次 `sha256sum`，验证 `hash_mismatch: stop_and_request_resync` 分支确实可触发（否则该契约属"未经执行的分支"，应降级为"未经测试"标注）。
